# 后端经验

记录后端开发中沉淀的可复用经验与约定，供后续任务参考。

## 跨模块共用的「当前账本」解析

多个业务模块（category、payee、tag、moneyflow）都有「取当前账本」的需求，历史上各模块各自写了一个私有 `getCurrentBookId()` / `getCurrentBook()`，并各自定义错误 key（`error.category.book.not.found`、`error.tag.book.not.found`、`error.payee.book.not.found`、`error.moneyflow.book.not.found`），文案完全相同。

**约定（避免重复）**：

- 统一收敛到 `BookService`，提供两个只读方法供其他 Service 注入复用：
  - `BookService.getCurrentBookId()`：校验当前账本存在且属于当前用户，返回 `Long`（仅需 ID 时用，内部走 `existsByIdAndUserId`）。
  - `BookService.getCurrentBook()`：同上，但返回完整 `Book` 实体（需要取记账币种等字段时用，内部走 `findByIdAndUserId`）。
- 错误 key 统一为 `error.book.not.found`（文案：当前账本不存在），不再按模块各起一个 key。
- 新增需要「当前账本」的模块时，直接注入 `BookService`，**不要**再复制私有 helper、也不要再定义 `error.<module>.book.not.found`。

原因：`getCurrentBookId` 的判空 + `existsByIdAndUserId` 校验逻辑、以及「当前账本不存在」这一语义，与具体模块无关，属于 `book` 领域的职责；重复定义会让同一语义散落在多个 key 上，改文案 / 改校验规则时需要同步多处。

## 前端已拦截的兜底校验统一用通用错误 key

后端存在一类「正常前端绝不会触发」的兜底校验：参数格式合法，但前端交互已保证不会传这类值（例如 moneyflow 中转账缺失转出账户、账户 id 不存在或不属于当前用户）。这类错误正常用户看不到，逐个定义语义 key（`error.moneyflow.account.required`、`error.moneyflow.account.not.found`）属于无意义散点。

**约定**：

- 此类「前端已拦截、后端仅兜底」的 `ResourceInvalidException` 场景，统一抛通用 key `error.invalid.argument`（文案：请求参数无效 / Invalid request parameter），不再按「模块.字段.原因」各造一个 key。
- 判断标准：该错误**用户能否通过正常操作触发并自行纠正**？
  - 能 → 保留精确 key（如分类类型不匹配、转入账户与转出账户相同），前端需据此给出可理解的提示。
  - 不能（前端已拦截、纯防御）→ 用通用 key `error.invalid.argument`。
- 后续若某个通用 key 场景开始需要区分排查，再单独抽出精确 key，并把旧引用迁走。

原因：兜底分支必须抛异常（否则后续流程会 NPE），抛通用 key 与抛精确 key 的代码量完全相同，差别只在 i18n 文件多几条条目；把「用户可见、可纠正」与「纯防御」两类错误分开——前者保留语义、后者收敛到单一 key，能避免 key 无意义增长。

**当前落地**：moneyflow 的「字段缺失 + 资源失效」类（`account/category/payee/tag/to.account` 的 `required`、`not.found`），以及 account / book / currency / category 各模块的「资源失效」类（`xxx.currency.not.found`、`currency.list.base.not.found`、`category.parent.not.found`）均已收敛到 `error.invalid.argument`；「业务规则约束」类（`category.type.mismatch`、`to.account.same` 等）保留精确 key。

**与 `error.validation.failed` 的分工**：`error.validation.failed` 专用于 `@Valid` Bean Validation 的字段格式/约束校验（返回带 `violations` 列表）；`error.invalid.argument` 专用于 Service 层 `ResourceInvalidException` 的资源引用失效/字段缺失兜底（返回单一 `message`）。两者同属 400，但来源与响应结构不同，勿混用。

## 有余额副作用的实体，删除/更新前先撤销其副作用

MoneyFlow 的 `create` 会在 `confirm=true` 时对账户余额 `applyBalance`（支出-、收入+、转账转出-转入+），因此删除/更新这类流水前必须先 `refundBalance`（`applyBalance` 的逆操作）撤销旧余额影响，再删除实体 / 套用新值，否则余额会残留旧额。

**约定**：

- `applyBalance` / `refundBalance` 只处理 type 1/2/3（支出/收入/转账），`type=4`（余额调整）天然 no-op——余额调整的历史流水只是追溯痕迹，账户余额在 `AccountService.adjustBalance` 里已直接覆盖为目标值，删除该痕迹**不能**再动余额。
- `MoneyFlowService.delete` 复用了这一套：`confirm=true` 时先 `refundBalance`，再 `moneyFlowRepository.delete`；标签关联靠实体上的 `cascade = CascadeType.ALL + orphanRemoval = true` 随主实体一并清理，无需手动删 TagRelation。
- 后续新增任何「会改动其他聚合状态」的实体（如月底结转、预算扣减），其删除/更新都要遵循「先撤销副作用 → 再操作实体」的顺序，且要明确哪些记录型数据（如历史痕迹）不能参与回滚。
## 退出登录：token 精确作废 + sessionInfo 按引用计数删除

会话存储是内存双 map：`CacheHolder.token`（token→userId）+ `CacheHolder.sessionInfo`（userId→SessionInfo），登录即 `createSession` 写入，此前无任何清理入口。`POST /logout` 落地后的关键约定：

- **作废粒度是单个 token，不是用户**：`SessionManager.invalidateSession(token)` 先 `token.remove(token)`；sessionInfo 以 userId 为键、多端登录共用一条，只有当 `!CacheHolder.token.containsValue(userId)`（该用户已无其他 token）时才删 sessionInfo。
- **不能无条件删 sessionInfo**：AuthInterceptor 只校验 token→userId 映射存在，随后 `SessionManager.getCurrentUser()` 直接 `sessionInfo.get(...).getCurrentUser()`——删了 sessionInfo 而其他端 token 仍在，那些端会 500（NPE）而非 401。
- **token 来源**：Controller 从请求头取（`WebUtils.resolveToken(request)`），`/logout` 走 AuthInterceptor（不在 WebConfig 排除列表），进来即 token 有效；token 无效时 `invalidateSession` 静默返回，接口幂等。
- 会话仍无过期时间：token 直到服务重启才自然消失，后续若做「记住我有效期 / 空闲超时」，应在双 map 上挂时间戳并在拦截器统一校验。

## Spring AI 2.x：运行时构建 ChatClient（用户自定义 LLM 配置）

LLM 配置存 `t_llm_config`（per-user），不走 `spring.ai.*` 启动期自动配置。要点（Spring AI 2.0.2，与 1.x 差异很大）：

- **API 变了**：1.x 的 `OpenAiApi` 已删除，2.x 基于官方 openai-java SDK。构建链：`ClientOptions.builder().httpClient(...).baseUrl(...).apiKey(...).build()` → `new OpenAIClientImpl(clientOptions)` → `OpenAiChatModel.builder().openAiClient(client).options(OpenAiChatOptions.builder().model(m).build()).build()` → `ChatClient.create(chatModel)`。
- **`ClientOptions` 唯一必填项是 `httpClient`**，用 Spring AI 自带的 `SpringAiOpenAiHttpClient.builder().build()`（全默认值可用：timeout/observationRegistry=NOOP 都有缺省）。
- **关闭自动配置**：starter 注册的 6 个 autoconfiguration 都有 `@ConditionalOnProperty(name="spring.ai.model.*", havingValue="openai", matchIfMissing=true)`，在 application.properties 设 `spring.ai.model.chat/embedding/image/audio.speech/audio.transcription/moderation=none` 即可全部关闭，避免无 api-key 时启动失败（不用 exclude 类）。
- **缓存**：`LlmClientFactory` 按 configId 缓存 ChatClient，命中时比对 (baseUrl, apiKey, model) 内容快照——BaseEntity 没有更新时间字段，内容快照就是最可靠的版本依据，改配置后自动重建，无需显式 evict（删除时才显式 evict）。
- **「当前使用」指针**：`User.currentLlmConfigId`，与 `currentBookId` 同构；activate 返回最新 `UserSessionVo`（复用 `UserService.buildUserSessionVo`，已改 public），与 `setBaseCurrency` 同口径。
- **删除语义**：允许删除使用中的配置（"无 AI 配置"合法），删除后指针置空——与账本（禁止删当前账本）不同。
- **测试连接**：`POST /llm-configs/test` 不保存直接测，一次真实 `prompt("ping").call()` 同时覆盖 baseUrl 可达/key 鉴权/model 存在；apiKey 留空时带 id 取库存 key 测（编辑弹窗不改 key 也能测）。
- 所有 AI 功能统一注入 `LlmClientFactory.currentClient()` 取当前用户的 ChatClient，未配置时抛 `error.llm.config.not.activated`。
- **OpenAiChatModel.builder() 必须同时给 `openAiClient` 和 `openAiClientAsync`**：只设 sync 版时，builder.build() 会对未设置的 async 客户端走默认构建（OpenAiSetup.setupAsyncClient → 重新 new ClientOptions，拿不到任何凭证），直接抛 "At least one credential source must be specified: credential (apiKey), workloadIdentity, or adminApiKey"——而且这个错发生在 ChatClient 任何一次调用上，与 baseUrl/key 是否正确无关。修法：`.openAiClientAsync(openAIClient.async())` 复用同一实例（openai-java 的 OpenAIClient 不继承 async 接口，但提供 async() 方法）。注意 test() 的 catch 会把一切异常包成 error.llm.config.test.failed 通用提示，具体原因要看后端 log.warn——排查 SDK 层问题要拿相同 classpath 写 main 方法复现完整调用链（只 build ClientOptions 不够，复现不出这个错）。
