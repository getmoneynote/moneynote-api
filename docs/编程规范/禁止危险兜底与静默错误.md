# 编程规范：禁止危险兜底与静默错误

## 1. 核心原则

编写代码时，不得为了让程序继续运行，而擅自为缺失、非法或异常的数据提供默认值。

**必须优先保证数据正确性、业务语义明确和错误可发现性，而不是单纯追求程序不报错。**

当程序缺少完成当前操作所必需的数据时，应明确暴露问题，而不是猜测数据应该是什么。

遵循以下原则：

1. **不猜测业务数据**：不得擅自为必需的业务数据设置默认值。
2. **不掩盖错误**：不得将非法数据、缺失配置或异常状态静默转换为正常结果。
3. **不吞噬异常**：不得为了避免报错而随意捕获异常、忽略异常或返回看似合理的结果。
4. **不混淆状态**：必须区分正常值、合法空值、数据缺失、数据非法和系统异常。
5. **明确业务规则**：默认值、容错、舍入、截断和降级行为必须有明确的业务依据。
6. **尽早失败**：当必需条件不满足时，应在最接近错误源的位置阻止操作。
7. **避免错误传播**：不得让错误数据继续流入计算、持久化或其他业务流程。

## 2. 禁止危险的默认值

### 2.1 必需业务数据不得自动补默认值

当一个字段是完成业务操作所必需的条件时，缺失就意味着当前操作无法被可靠执行。

禁止：

```javascript
const decimalPlaces =
  currentRow?.currencyDecimalPlaces ?? 2;
```

如果币种小数位数是金额换算的必要条件，不得在缺失时擅自使用 `2`。

推荐：

```javascript
if (!currentRow) {
  throw new Error('账户数据不存在或尚未加载');
}

const decimalPlaces = currentRow.currencyDecimalPlaces;

if (
  !Number.isInteger(decimalPlaces) ||
  decimalPlaces < 0
) {
  throw new Error('币种小数位数缺失或无效');
}
```

实际代码应根据执行阶段区分加载状态与业务异常，不应把正常的异步加载过程误判为系统错误。

### 2.2 不得将技术上的方便当作业务依据

以下写法需要特别审查：

```javascript
value ?? defaultValue
value || defaultValue
Number(value) || 0
amount || 0
items ?? []
config ?? {}
```

这些写法本身并非一律禁止，但必须确认默认值具有明确的业务含义。

例如：

- 金额缺失时自动补 `0`，可能把未知金额变成零金额。
- 币种缺失时默认使用人民币，可能导致金额解释错误。
- 权限配置缺失时默认允许操作，可能造成安全问题。
- 账户关联关系缺失时使用第一个账户，可能将交易记入错误账户。
- 汇率缺失时默认使用 `1`，可能导致金额转换错误。
- 分页参数缺失时采用明确规定的默认页码，可以是合理设计。

判断标准不是代码能否编译，而是**该默认值是否经过业务规则明确授权，以及使用它是否会改变数据的含义**。

## 3. 严格区分不同的数据状态

不得将以下状态混为一谈：

| 状态 | 含义 | 推荐处理方式 |
|---|---|---|
| 合法业务值 | 数据存在且符合规则 | 正常处理 |
| 合法的零值 | 例如余额为 0、数量为 0 | 保留零值 |
| 合法空值 | 业务明确允许不填写 | 保留空值，按业务规则处理 |
| 尚未加载 | 异步数据仍在获取 | 等待加载或显示加载状态 |
| 必需数据缺失 | 完成操作所需的数据不存在 | 阻止操作并暴露错误 |
| 数据格式非法 | 数据类型、格式或范围不符合约定 | 拒绝处理并报告错误 |
| 外部服务异常 | 数据库、网络或第三方服务失败 | 按明确的错误策略处理 |

禁止通过一个统一的默认值或空值返回机制处理所有状态。

## 4. 禁止静默转换非法数据

不得在没有明确业务规则的情况下，将非法数据转换成合法数据。

禁止：

```javascript
const amount = Number(input) || 0;
```

该写法会将多种不同情况转换成 `0`，包括空字符串、非法数字和数值 `NaN`，使调用方无法区分真正的零金额与错误输入。

推荐根据业务契约进行校验：

```javascript
function parseAmount(value) {
  if (value === null || value === undefined || value === '') {
    throw new Error('金额不能为空');
  }

  const amount = Number(value);

  if (!Number.isFinite(amount)) {
    throw new Error('金额格式无效');
  }

  return amount;
}
```

如果某个表单字段允许为空，应在表单适配层明确处理空值，而不是让核心解析函数猜测调用方的意图。

同样需要避免以下行为：

- 非法日期自动替换为当前日期。
- 未知枚举值自动映射为默认枚举。
- 不存在的关联实体自动替换为第一条记录。
- 超出范围的数值自动截断。
- 数据解析失败时返回空对象。
- 计算失败时返回零或空字符串，且不留下任何错误信息。

## 5. 禁止静默吞噬异常

禁止通过空的 `catch` 块或无依据的兜底返回值掩盖异常。

禁止：

```javascript
try {
  return calculateAmount(value);
} catch (error) {
  return 0;
}
```

这会把计算失败伪装成金额为零。

推荐：

```javascript
try {
  return calculateAmount(value);
} catch (error) {
  logger.error('金额计算失败', error);
  throw error;
}
```

如果当前层能够提供更有价值的业务上下文，可以包装异常，但必须保留原始异常及其原因。

只有在业务明确允许降级、回退或忽略某种失败时，才可以捕获异常并继续执行。此时必须明确降级条件、行为和必要的日志或监控。

## 6. 默认值必须有明确的业务依据

默认值并非绝对禁止，但必须符合以下条件：

1. 默认值由明确的业务规则、产品需求或技术协议定义。
2. 默认值的语义与缺失值的语义一致，不会改变业务含义。
3. 使用默认值不会掩盖必须处理的配置错误或数据异常。
4. 默认值的适用范围和生效条件清晰。
5. 对重要业务行为，默认值应有相应的测试覆盖。

例如：

```javascript
// 合理：产品规定新建列表默认显示第一页
const page = requestedPage ?? 1;
```

但如果分页参数是由必需的外部协议保证存在的，那么缺失时是否采用默认值，仍应根据协议和业务约定决定。

不得因为某个默认值在大多数场景下有效，就认定它在所有场景下都安全。

## 7. 校验应放在正确的层次

应根据数据的来源和用途决定校验位置。

### 7.1 输入边界

对用户输入、外部 API 响应、数据库读取结果和配置文件进行必要的格式、类型及范围校验。

### 7.2 业务层

校验业务操作所需的前置条件，包括实体是否存在、关联关系是否完整、状态是否允许执行操作。

### 7.3 核心计算层

保证计算函数的参数满足明确的契约，不允许非法参数在计算过程中被静默修正。

### 7.4 展示层

可以处理加载中、合法空值和展示格式，但不得将业务错误转换为看似正常的显示结果。

避免在每一层重复实现相同的业务逻辑。应由明确的边界负责数据校验，由核心函数保证自身契约，由业务层决定操作是否允许继续。

## 8. 金额与财务数据的特殊要求

MoneyNote 涉及金额、币种、汇率、账户余额和交易记录。此类数据必须采用更严格的处理标准。

1. 金额必须有明确的币种语义。
2. 金额换算必须使用有效的小数位数或明确的精度规则。
3. 缺少币种、汇率或其他必要配置时，不得擅自使用 `2`、`0` 或 `1` 等默认值。
4. 最小货币单位的存储格式必须符合项目约定。
5. 不得将非法金额转换为零金额。
6. 不得在没有明确规则的情况下自动四舍五入、截断或改变用户输入。
7. 必须考虑 JavaScript `Number` 的安全整数限制，不能假设所有 Java `Long` 值都能被前端精确表示。
8. 金额计算、精度校验、舍入规则和展示格式应有明确的职责边界。
9. 对金额转换、余额变更和交易写入等关键操作，应有相应的边界测试。

## 9. 错误必须具有可发现性

发现错误后，应选择与当前场景相匹配的处理方式：

- 对用户输入错误，提供明确的校验提示。
- 对缺失的业务前置条件，阻止当前操作。
- 对违反程序契约的情况，抛出明确异常。
- 对外部服务失败，返回符合接口约定的错误结果。
- 对需要运维关注的系统故障，记录必要的上下文和错误信息。

不要为了让界面继续显示或让接口返回成功状态，而隐藏错误。

错误信息应说明发生了什么、涉及哪个业务对象，以及在必要时如何定位问题。不得在日志中泄露密码、密钥等敏感信息。

## 10. 修改现有代码时的要求

发现危险兜底时，不要只删除默认值，而应完成必要的影响分析。

修改前：

1. 找出相关函数的所有调用位置。
2. 确认参数来源和现有调用约定。
3. 区分合法空值、加载状态和异常数据。
4. 明确缺失或非法数据应该如何处理。
5. 检查修改是否会影响其他业务流程。

修改时：

1. 删除没有业务依据的兜底。
2. 增加必要的参数校验和业务前置条件检查。
3. 修改依赖旧行为的调用位置。
4. 保持正常业务行为不变。
5. 对关键边界情况增加测试。

修改后：

1. 检查是否仍存在相同类型的危险兜底。
2. 验证零值、空值、非法值和边界值。
3. 确认错误不会被下游代码再次吞噬。
4. 确认异常处理不会造成数据部分写入或状态不一致。

不得为了快速通过测试而将异常改成默认值，也不得为了消除报错而绕过必要的校验。

## 11. AI 编程的强制要求

在使用 AI 编写、修改或审查代码时，必须遵循本规范。

AI 不得擅自：

- 为缺失的业务数据补充未经授权的默认值。
- 将异常返回值改为 `0`、空字符串、空对象或空集合以消除报错。
- 为了兼容未知情况而随意增加 `??`、`||` 或空 `catch`。
- 将数据校验失败改成静默跳过。
- 在不了解调用方语义时改变函数的错误处理契约。
- 仅修改报错位置而忽略数据来源和其他调用位置。

遇到缺失值时，AI 必须先判断该值是合法可选项、尚未加载的数据，还是业务必需数据。

如果业务规则尚不明确，不得自行猜测。应优先检查现有代码、实体定义、接口约定和项目文档；仍无法确定时，应明确指出需要确认的业务规则。

在提交修改前，应说明重要兜底的删除或保留理由，以及相关影响范围和测试结果。

## 12. 代码审查清单

提交代码前，应检查以下问题：

- [ ] 是否为必需的业务数据设置了未经授权的默认值？
- [ ] 是否把缺失数据、非法数据或异常状态转换成了正常值？
- [ ] 是否把合法的零值错误地视为缺失值？
- [ ] 是否混淆了加载状态与业务异常？
- [ ] 是否通过 `catch`、空字符串、零值或空对象掩盖错误？
- [ ] 是否存在未经明确规定的舍入、截断或自动纠正？
- [ ] 是否验证了核心函数的输入契约？
- [ ] 是否分析了所有相关调用位置？
- [ ] 是否对关键边界情况增加了测试？
- [ ] 是否有充分的业务依据支持保留的默认行为？

## 13. 最终判断标准

当代码遇到缺失值、非法数据或异常状态时，必须先判断其业务含义，再决定如何处理。

**宁可明确暴露一个真实错误，也不要通过未经授权的默认值制造一个表面正常、实际错误的结果。**

代码的目标不是让所有情况都能继续执行，而是确保只有满足业务规则的操作才能可靠地执行。

对于不允许猜测的业务数据，失败必须明确、可定位、可测试；对于业务允许为空或允许降级的情况，必须有清晰的规则和边界。

本规范的最终目标是：让错误尽早暴露，让数据含义保持明确，让业务行为可预测，并防止静默错误在系统中持续传播。
