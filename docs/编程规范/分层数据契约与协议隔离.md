# 编程规范：分层数据契约与协议隔离（以 chat / agent 为例）

> 适用范围：`backend/src/main/java/com/moneynote/chat`、`web-pc/src/pages/aiAssistant`、`web-pc/src/api/message.js`，以及所有新接入的大模型能力。
> 定位：本文是**规范**（讲为什么、规定必须/禁止）；现网的具体类、字段与事件全集**以代码为准**（`chat.agent.AgentEvent` / `chat.event.ChatEventType`）。两者冲突时以代码为准；本文用于审查新代码和方案。
> 一句话结论：**每一层自己定义数据类、事件和契约，跨层只传「本层专门产出的契约对象」；上游原始对象不得透传，下游技术不得反向写入上层代码。**

---

## 1. 核心思想

**职责分工**：大模型负责理解和决策，Agent 负责组织执行，后端负责数据转换与状态管理，前端负责渲染与交互。

Agent 的延迟高、成本高，因此架构上的目标不是「让模型多做一点」，而是**让每一层都能把不必要的工作挡在模型之前**（见第 7 节）。

三条不可混同的协议：

| 协议 | 谁产出 | 表达什么 | 绝不能流向 |
|---|---|---|---|
| 模型协议 | 大模型服务商 / Spring AI | token、思考片段、原始 tool call、`finish_reason` | SSE、React |
| 业务行为 | Agent | 这一步在业务上发生了什么 | 直接当作渲染指令 |
| 交互协议 | 后端聊天层 → SSE | 前端这一刻需要知道什么 | 反向被 Agent 依赖 |

由此得到四条硬约束：

1. **模型层不应该知道 React**，Agent 层不应该知道 Ant Design，前端也不应该知道模型供应商的原始响应格式。
2. **不要让大模型直接决定前端应该如何渲染 HTML**，也不要让前端直接依赖大模型供应商的数据格式。
3. **不要让 SSE 直接暴露大模型协议**：SSE 输出的是前后端交互协议，不是 `ChatResponse` 的另一种序列化。
4. **每一层只负责自己的事情**：数据类、事件、错误语义、状态都归该层私有，互不干扰。

### 1.1 三个必须分离的职责

- **SSE 负责传输事件**：只把 `ChatEvent` 逐帧写出，不生成业务语义、不拼接内容、不判定终态。
- **事件描述「当前发生了什么」**：`eventType` + 载荷说明事实，不说明「前端该画什么」。
- **前端根据事件类型决定如何渲染，后端维护 Agent 与会话的状态**：前端不推断终态、不自造 id；后端不写渲染指令。

本项目当前没有会话实体（2026-11-08 起移除），「会话状态」指 `(user_id, agent_code)` 固定时间线、`Message.status`（GENERATING / COMPLETED / ERROR / STOPPED）与落库事务，全部由后端 `ChatTransactionService` / `TerminalFinalizer` 维护。

## 2. 分层与依赖方向

用户口径的「四层」是：大模型服务商 / Spring AI / Agent / 与前端交互的 SSE。工程落地时，SSE 与 Agent 之间还有**聊天与编排层**（状态管理），前端是最终消费者，因此按下面六个边界段描述。段数不重要，重要的是**每段都有自己的数据类，且每两个段之间有且仅有一个显式转换点**。

```
  数据流方向：模型 ──────────────────────────────────────────────► 用户
  依赖方向：  前端 ──► 交互协议 ──► 领域事件 ──► 框架对象 ──► 供应商原始协议

  React 前端（渲染/交互）
   自有：ChatEventType 常量 / onEvent 分发 / Bubble.List 渲染器表 / 本地轮次状态
    ▲ ① message.js 解析 SSE 帧 → 按 eventType 分发（前端自己做转换）
  ─────────────────────── 交互协议边界 ───────────────────────
  SSE / ChatEvent：{eventType, messageId, seq, eventData}
   自有：ChatEvent / ChatEventType / payload.* / ServerSentEvent
    ▲ ② SseTransport.toSse（帧）；ChatEventConverter + ChatEventFactory（映射/发号）
  ─────────────────────── 聊天层边界 ─────────────────────────
  聊天与编排层（状态、事务、生命周期）
   自有：Message / Message.status / MessageDraft / GenerationPipeline / GenerationInput
    ▲ ③ AgentOrchestrator 只认 Agent 接口，不认具体实现类
  ─────────────────────── Agent 边界 ─────────────────────────
  Agent 领域协议
   自有：AgentRequest / AgentContext / AgentEvent(sealed) / AgentExecution / 各 Agent 私有 tool、dto
    ▲ ④ ChatResponseParser → ReasoningNormalizer → ChatResponseProcessor（唯一一份，归 Agent 层）
  ─────────────────────── 框架适配边界 ───────────────────────
  Spring AI 对象：ChatResponse / AssistantMessage / Generation / ToolCallback / ChatClient
    ▲ ⑤ 供应商 SDK / 线路 SSE
  ─────────────────────── 供应商边界 ─────────────────────────
  大模型服务商原始协议：choices[].delta / reasoning_content / tool_calls / finish_reason
```

**术语**：靠近用户的一侧叫上层，靠近模型的一侧叫下层。数据流自下而上；**上层可以认识下层暴露出来的契约，下层绝不能认识上层的任何类型**。

**两条依赖规则**：

- **谁消费，谁转换**：适配器归消费方所有，转换结果是消费方自己的类型。④ 的解析器在 `chat.agent` 根包而不是聊天层，② 的映射器在 `chat.event` 而不是 Agent 层，① 的帧解析在 `web-pc/src/api/message.js` 而不是后端。上游永远不负责「替下游格式化好」。
- **禁止公共万能 DTO**：不允许建一个 `CommonChatDTO` / `Map<String,Object>` 让所有层共用。`ChatEvent.eventData` 声明为 `Object` 只是为协议扩展留出形状，其合法性由 `ChatEventFactory` 用 `ChatEventType.payloadType()` 在唯一构造点强制校验，不是放任透传。

| 层 | 可以依赖 | 禁止出现 |
|---|---|---|
| Spring AI / 供应商 | 供应商 SDK | `AgentEvent`、`ChatEvent`、React/UI、数据库 |
| Agent 层 | `ChatClient` / `ChatResponse`、业务 Service、共享解析器 | `ChatEvent`、`ServerSentEvent`、Repository、`@Transactional`、`CurrentUserHolder`、任何 UI 名 |
| 聊天/编排层 | Agent 接口与 `AgentEvent`、`ChatEvent`、Repository、事务 | Agent 具体实现类、供应商原始字段 |
| 传输层 | `ChatEvent`、`SseTransport` | 其余一切 |
| 前端 | `ChatEventType` 常量与载荷结构 | `ChatResponse` / `AssistantMessage` / `choices[].delta` / 供应商 `tool_calls` / HTML 片段 |

## 3. 事件链：`AgentEvent` 不是 `ChatEvent`

```
Agent ──► AgentEvent ──► ChatEventConverter ──► ChatEvent ──► SseTransport ──► SSE ──► React onEvent ──► 渲染
         （领域事件）      （用户口径的 ChatEventMapper）   （协议事件）
```

> 命名对照：用户/早期方案里的 `ChatEventMapper`、`ChatStreamEventMapper` 在现网对应 `chat.event.ChatEventConverter`（P0 重构后 `ChatStreamEventMapper` 已删除）。

一句话区分：

- **`AgentEvent` = Agent 内部发生了什么**：正文增量、思考增量、结束原因。
- **`ChatEvent` = 前端需要知道什么**：`start / reasoning / content / finish / error` + `messageId` + `seq`。

| 维度 | AgentEvent | ChatEvent |
|---|---|---|
| 产出方 | Agent / 工具 | 聊天层（`ChatEventFactory`、`GenerationPipeline`） |
| 语义范围 | 单次执行内部，可携带只有 Agent 知道的信息 | 一次对话对外公开的事实 |
| 身份与序号 | 不知道 messageId、不分配 seq | 带 messageId、seq，由唯一发号点分配 |
| 终态 | **刻意没有** Start / Complete / Error | 有 `start` / `finish` / `error` |
| 表达方式 | `sealed interface` + record，无 `default` 分支 | 封闭枚举 `ChatEventType` + `payload/` 载荷 |

三条由此派生的规则：

1. **终态归后端，Agent 无权宣布成功或失败**。本项目的「成功」定义是落库成功（`Message.STATUS_COMPLETED`），Agent 既不知道消息 id 也不知道事务边界。Agent 执行失败用响应式流的 `onError` 表达，由 `GenerationPipeline` 转成 `error` 事件；`finish` 必须在终态落库**完成后**才发出，前端收到即可安全刷新。
2. **元数据不单独占用协议事件**。`AgentEvent.FinishReason` 只携带 provider 的 `stop / length / content_filter`，由 `MessageDraft.observe` 提取后经 `finish` 载荷透出，转换器返回 `Flux.empty()`；不为了「完整」把它做成一条 SSE 事件。
3. **框架知识只存在一份**。Spring AI 2.0.2 会把 `reasoning_content` 跨 chunk 累计成全文快照，这一段适配知识只放在 `ChatResponseParser` / `ReasoningNormalizer` / `ChatResponseProcessor`，由 `AbstractLlmAgent` 统一调用。任何「每个 Agent 自己解析一遍」或「前端自己按前缀去重」的写法都是错的。

`sealed` + 模式匹配 `switch` 不写 `default`，是为了让「新增事件类型」由编译器强制所有分发点同步处理，杜绝「加了事件但某个分发点静默丢弃」。

## 4. 禁止清单：不要让 SSE 暴露大模型协议

### 4.1 Controller / Service 直接吐框架对象

```java
// 禁止：SSE 帧里出现 Spring AI 类型
@PostMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<ChatResponse>> send(...) {
    return client.prompt()...stream().chatResponse().map(...);
}

// 正确：Controller 只认识 ChatEvent，帧构建交给唯一转换点
public Flux<ServerSentEvent<ChatEvent>> send(...) {
    return messageService.send(agentCode, form).map(sseTransport::toSse);
}
```

同理，禁止把 `ChatResponse`、`AssistantMessage`、`Generation.metadata`、`usage` 或供应商 `tool_calls` 的原始 JSON 塞进 `eventData`「先透出去，以后再整理」。协议一旦上线就是对外契约，临时透传会变成永久依赖。

### 4.2 Agent 越界

```java
// 禁止：Agent 返回协议事件、分配 seq、决定终态、直接落库
Flux<ChatEvent> stream(AgentRequest req, AgentContext ctx);

// 正确：Agent 只表达领域事件，冷流、订阅才触发模型调用
Flux<AgentEvent> stream(AgentRequest req, AgentContext ctx);
```

Agent 不创建/保存消息、不建 SSE 连接、不做取消处理、不宣布终态；`start / finish / error` 由聊天层产生。工具线程上不查 `CurrentUserHolder`（ThreadLocal 在那里是 null），`userId`、`bookId`、`now`、`client` 由请求线程算好放进 `AgentContext` 显式传递。

### 4.3 前端理解供应商格式

```javascript
// 禁止：前端解析服务商原始字段
onEvent: ({ eventType, eventData }) => {
  setText(eventData.choices[0].delta.reasoning_content);
  setTools(eventData.choices[0].delta.tool_calls);
};

// 正确：前端只按自己的 eventType 分发
onEvent: ({ eventType, eventData }) => {
  switch (eventType) {
    case ChatEventType.REASONING: /* 追加思考 */ break;
    case ChatEventType.CONTENT:  /* 追加正文 */ break;
    case ChatEventType.ERROR:    /* 展示错误 */ break;
    default: break;
  }
};
```

前端可以镜像一份 `ChatEventType` 常量，但**后端 `ChatEventType.wireName()` 是事实来源**，新增/改名必须同一次上线。前端不得因为「后端字段多，先直接用」而依赖非协议字段。

### 4.4 模型直接决定渲染

```json
// 禁止：模型输出 HTML / 组件名 / class / 样式 / 脚本，前端 dangerouslySetInnerHTML
{ "type": "moneyflow_draft", "html": "<div class='ant-card'>...</div>" }
```

Markdown **文本**可以作为 `content` 事件由前端渲染（文本是内容，不是渲染决策），但 Markdown 渲染器必须关闭原始 HTML 通道；结构化展示当前未实现（见第 5 节）。

| 禁止 | 后果 | 正确做法 |
|---|---|---|
| SSE 透传 `ChatResponse` / `tool_calls` | 换供应商、升 Spring AI 就要改前端 | 边界适配器转成 `AgentEvent` → `ChatEvent` |
| 事件里带渲染指令 | 模型能改界面结构，逻辑与样式失控、XSS | 只带语义类型 + 业务数据 |
| `AgentEvent` 里出现 `ChatEvent` / seq | 领域层被传输协议绑死 | 终态与发号由聊天层负责 |
| 前端自行推断终态 | 落库未完成时刷新，看到半截/幽灵消息 | 只认 `finish` / `error` |
| 后端在事件里拼「前端展示文案」 | 多语言、主题、组件库反向侵入后端 | 发语义码与数据，文案由前端 i18n 决定 |

## 5. 结构化展示：当前不做，也不要留占位

现网 `AgentEvent` 只有正文增量、思考增量、结束原因三种领域事件，SSE 只有
`start / reasoning / content / finish / error` 五类事件，**没有卡片、表单、分段块等
结构化展示能力**。曾为它们预留的领域事件与协议分支已于 2026-11-10 删除——
零发送方的类型只会让「协议里有哪些事件」变得不可信。

将来真要做，按第 8 节的清单一次性补齐：后端加事件常量与载荷、Agent 层加领域事件、
`ChatEventConverter` 补 sealed 分支、前端加渲染与 `case`，并同时落地交互端点；
不要先留一个没人发的 record 或恒抛异常的分支。第 4.4 节「模型不产 HTML」、
第 9 节「写操作必须经用户确认的普通业务端点」在任何实现方案里都是硬约束。

## 6. 三个职责的落地位置

| 职责 | 归属 | 现网实现 |
|---|---|---|
| 传输事件 | 传输层 | `SseTransport.toSse`；`event:` 字段与 JSON 内 `eventType` 一致 |
| 描述发生了什么 | 协议层 | `ChatEventType`（`wireName` 显式声明，不从枚举名推导）+ `payload/` 三个 DTO + `ChatEventFactory` 配对校验 |
| 决定如何渲染 | 前端 | `messageApi.send` 解析帧 → `onEvent` switch → `activeRound` 本地状态 → `Bubble.List` / `Think` / `XMarkdown` |
| 维护状态 | 后端聊天层 | `ChatTransactionService` 三阶段短事务、`Message.status` 唯一终态、`MessageDraft` 缓冲、`TerminalFinalizer` 终态 CAS、`ChatEventFactory` 发 seq |

推论：`finish` 在落库完成后发出，因此**前端收到 `finish` 才代表服务端状态已定**；中止对应落库 `STOPPED` 且无事件（连接已断），前端不能靠「流断了」自行判定成败。换传输协议（SSE → WebSocket）时只应改 `SseTransport` 与 `MessageController`，上面三层零改动。

## 7. 成本与延迟：三层漏斗 + 上下文管理

Agent 每次调用都是钱和秒级延迟。优化顺序永远是**先把请求挡在更便宜的层**，而不是先去调更快的模型。

**第一层 · 规则层（零模型调用，确定性）**
- 能用代码判定的，绝不问模型：参数校验、`AgentRegistry.requireRegistered` 白名单、幂等、缓存命中、权限与金额口径。
- 现网实例：**用户从菜单选 Agent 取代 `RouterAgent` 的 LLM 意图分类**，直接省掉一次模型调用、首字延迟与路由误判；`AgentOrchestrator.dispatch` 只查表不做意图判断。
- 现网实例：`AccountAnalysisResponse` 的总资产/总负债/净资产由 Java 按本位币算好，模型直接引用，不让模型自己加总或乘汇率（既慢又容易算错）。
- 反模式：把「这条消息属于哪个 Agent」「金额是否合法」「汇总值是多少」交给模型决定。

**第二层 · 上下文层（少送 token）**
- **上下文窗口**：当前是全量历史，属已知技术债；加窗口时五处扩展点必须同步（`Message`、`MessageRepository`、`ChatTransactionService.initialize`、`MessageService.list`、`messageApi.list`），保证「用户看到的」与「模型看到的」是同一段历史。
- **工具 DTO 裁剪**：只给模型必要字段（`AccountAnalysisResponse` 不含卡号、支付能力标记），别把整张实体序列化进 prompt。
- **展示数据不进上下文**：仅用于渲染的结构化数据不回灌给模型；提示词写「范围守卫」，越界固定拒答，不代答不编数据。
- 反模式：每轮重发全量历史、工具返回大段冗余文本、为「更聪明」额外加一次路由模型调用。

**第三层 · 模型层（最后才用，且一次）**
- 流式输出降低首字延迟；按当前用户的 `LlmConfig` 选模型，配置在请求线程解析后放进 `AgentContext`。
- 一次生成只发起一次模型调用；失败不要无脑重试（成本翻倍，且写路径会重复写库）。
- 反模式：串联多个 LLM 决策、把结构化输出再让模型「复述一遍」、用模型做本可确定性完成的补全。

## 8. 变更影响面（用来验收隔离是否成立）

「互不干扰」不是口号，验收方式是看**一次改动需要碰几个层**。

| 改动 | 应该只改 | 不应该波及 |
|---|---|---|
| 换模型供应商 / 升 Spring AI | `ChatResponseParser`、`ReasoningNormalizer`、`ChatResponseProcessor` | Agent 实现、协议、前端 |
| 新增一个 Agent | 新包（Agent + 私有 tool/dto）、`resources/prompts/<name>/system.md`、注册表装配、前端菜单映射 | 编排层、协议层、其他 Agent |
| 新增协议事件 | `ChatEventType` 加常量 + `payload/` 加 record + `ChatEventFactory` 加语义方法 + `ChatEventConverter` 补 sealed 分支 + 前端补一个 `case` | `ChatEvent` 信封、任何编排类 |
| 换 UI 组件库 | 前端页面 | 后端全部 |
| 换传输协议 | `SseTransport` + Controller | 上面三层、前端事件分发语义 |

新增事件时，`sealed` 与「switch 不写 default」会让编译器把所有遗漏的分发点直接报出来——这是刻意设计的，不要用 `default` 或 `catch` 把它绕过去。

## 9. AI 编程的强制要求

使用 AI 编写、修改或审查大模型相关代码时：

- 不得把 `ChatResponse` / `AssistantMessage` / `Generation` / 供应商 `tool_calls` 原始结构透传到 SSE 或前端，即使只是「临时联调」。
- 不得让模型输出 HTML、组件名、样式或脚本；不得在前端用 `dangerouslySetInnerHTML` 渲染模型产物。
- 不得让 Agent 返回 `ChatEvent` / `ServerSentEvent`、分配 `seq`、判定终态或直接落库。
- 不得为了少写几个类而建跨层万能 DTO、把 `Map` 当契约，或让前端直接读协议之外的字段。
- 不得把写库方法注册为 LLM 工具；写操作必须经用户确认的普通业务端点。
- 不得用 `default` 分支、空 `catch` 或「先透传以后再整理」绕过 sealed 分发与协议校验。
- 遇到「模型能不能顺手做掉」的需求，先判断是否属于规则层/上下文层；属于的，用确定性代码解决，不要新增一次模型调用。
- 涉及协议变更时，必须同时列出后端枚举、转换器、前端常量的改动点；不能只改一侧。

## 10. 代码审查清单

- [ ] 每一层的数据类是否只在该层内部使用？有没有跨层共用的万能 DTO？
- [ ] SSE 载荷里是否出现任何 Spring AI / 供应商原始类型或字段名？
- [ ] 前端是否只按 `eventType` 分发，且没有解析 `choices` / `delta` / `reasoning_content` / `tool_calls`？
- [ ] `AgentEvent` 是否只表达领域事件，不含终态、messageId、seq、UI 概念？
- [ ] `start` / `finish` / `error` 是否由聊天层产生？`finish` 是否在落库完成后发出？
- [ ] 每个边界是否只有一个转换点，且适配器归消费方所有？
- [ ] 框架/供应商的适配知识（解析、累计归一、字段位置）是否只有一份实现？
- [ ] 事件类型是否封闭枚举、`wireName` 是否显式声明、载荷是否有配对校验？
- [ ] 新增事件时所有 sealed 分发点是否同步补齐（没有 `default` 兜底）？
- [ ] 模型产物是否只有文本，没有 HTML / 组件名 / 样式 / 脚本，前端未用 `dangerouslySetInnerHTML`？
- [ ] 写库方法是否未注册给 LLM，写操作是否经用户确认的普通业务端点？
- [ ] 状态（消息状态、时间线、缓冲、seq）是否全部由后端维护，前端没有自行推断终态？
- [ ] 本次改动是否把本可规则化/上下文化的问题又交给模型多跑了一次？
- [ ] 未知类型/异常是否有协议明确规定的降级，而不是静默丢弃或整页崩溃？
