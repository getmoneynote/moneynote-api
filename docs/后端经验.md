# 后端经验

## MoneyFlow 查询优化：避免重复数据库查询（2026-10-15）

### 问题
在 `MoneyFlowService` 中，`buildSpec` 内调用 `bookService.resolveBook(form.getBookId())` 仅为获取账本币种的小数位，用于把 `minAmount`/`maxAmount` 从主单位换算成最小单位。这个调用在 `query()` 和 `statistics()` 中都会执行，且 `resolveBook` 本身可能再查一次库。如果 `bookId` 为空，还会走 `getCurrentBook()` 逻辑（再查 user session + book 表）。

### 解决方案
1. **修改 `buildSpec` 方法**：添加 `amountFilterCurrency` 参数，当提供时直接使用该币种进行精度换算，否则调用 `resolveAmountFilterCurrency(form)`
2. **条件化货币解析**：只在 `minAmount` 或 `maxAmount` 非空时才需要计算精度，否则跳过货币解析
3. **更新调用方**：在 `query()` 和 `statistics()` 中，只有当需要金额区间过滤时才解析货币并传入 `buildSpec`

### 关键代码位置
- `MoneyFlowService.java:263-341` - `buildSpec` 方法
- `MoneyFlowService.java:165-177` - `query` 方法  
- `MoneyFlowService.java:183-228` - `statistics` 方法

### 效果
- **当 `minAmount`/`maxAmount` 为空时**：完全避免数据库查询获取账本币种
- **当 `minAmount`/`maxAmount` 设置时**：仅执行一次必要的数据库查询（而非每个方法各一次）

该优化保持了功能完全一致，同时减少了不必要的数据库访问，尤其在列表查询中常见的无金额过滤场景下性能提升显著。

## options 接口约定：下拉数据源不走分页 list（2026-10-21）

### 背景
前端表单的下拉数据源曾直接调分页 list 接口硬凑（`size: 1000` 拉全量）。问题：
1. **契约脆弱**：分页接口不承诺"返回全部"，数据超过 1000 条时下拉静默缺项；后端改分页默认值/排序会悄悄改变下拉构成
2. **字段过重**：list 是管理视角（如 `AccountListItem` 含 20 字段、含本位币换算），下拉只需其中几个
3. **职责错位**：哪些账户能进支出/转账下拉（`canExpense` 等用途开关）是业务规则，客户端过滤会散落复制、规则不一致
4. **排序漂移**：`AccountController.list` 默认按 `balance` 倒序，每记一笔账下拉顺序就跳动；下拉需要稳定排序

### 约定
- 下拉数据源一律走 **`GET /{resources}/options`**：轻量、不分页、返回数组（`DataResponse`），配套前端全局缓存 hook（参考 `useCurrencyOptions` 的 cache + ensureLoaded/refresh 模式）
- **可过滤**：options 带查询参数（如 `AccountOptionQueryForm` 的 `type` + 四个 `canXxx`），过滤规则收敛在后端。语义与旧版 `cn.biq.mn.account.AccountQueryForm` 一致：传值即等值过滤，不传不限制
- **稳定排序**：按**对 user 唯一**的字段升序（currency 按 code，account 按 name），不用随业务变动的字段（balance）。理由同 `CurrencyService.listOptions` 的注释：无 ORDER BY 时各数据库返回顺序不定
- **小数据量资源在内存过滤**：单用户账户量级小（几十条），options 直接复用 `findByUserId` 查全量，type/canXxx 过滤和排序统一在 service 层 stream 完成，不为 options 专门增加 repository 方法。数据量可能大的资源不适用此条，仍应在查询层过滤
- **type 参数超范围不报错**，返回空列表（与 `query()` 一致，见 `AccountService.isInvalidType`）
- options 查询参数单独建 Form 类（`AccountOptionQueryForm`），不混入 `AccountQueryForm`——list 是管理视角，options 是可选视角，契约分开演进
- N+1 防护与 `query()` 同策略：一次性加载用户全部币种进 Map，不在 map 内逐个懒加载

## 消息发送（同步 LLM 调用）的落库模式（2026-10-30）

- **单事务全有或全无**：`MessageService.send` 里「存用户消息 → 调 LLM → 存助手消息」在一个
  `@Transactional` 内，LLM 失败整体回滚（用户消息也不留），前端报全局错误后用户重发。
  代价是失败时用户消息不落库；将来要保留需把 LLM 调用挪到事务外。
- **`Conversation.updatedAt` 必须显式 `setUpdatedAt(Instant.now())`**：新增 Message 行不会触碰
  会话行，`@UpdateTimestamp` 只在会话本身 dirty 时生效（实体注释已写明，这里是最初的落地处）。
- **`LlmClientFactory` 拆出 `currentConfig()`**：`currentClient()` 委托 `cachedClient(currentConfig())`；
  调用方要拿配置本体（如 model 快照落库）时用 `currentConfig()`，别重复写「SessionManager 取
  currentLlmConfigId + 判空 422」这套逻辑。
- **`com.moneynote.chat.Message` 与 `org.springframework.ai.chat.messages.Message` 同名冲突**：
  Service 里不 import Spring AI 的 Message，用全限定名 + 注释说明（见 `MessageService.toAiMessage`）。
- **Spring AI 历史消息回放**：`chatClient.prompt().messages(List<org.springframework.ai.chat.messages.Message>).call().content()`，
  我方 role 1/2 → `UserMessage` / `AssistantMessage`（spring-ai 1.1.2，类在 `spring-ai-model` 包）。

## 聊天流终态落库的两个兜底缺陷（已修复 2026-11-03）

### 背景
评审建议"模型失败与落库失败分开处理、引入 PERSIST_FAILED 状态和任务存储"。
对照代码推演后发现建议过度设计，但暴露出两个真实缺陷。

### 缺陷与修法
1. **CAS 占位 ≠ 落库成功**：`MessageService.persistTerminal` 先 `compareAndSet` 占位再写库，
   写库抛异常时占位已被消费，`onErrorResume` 的兜底 ERROR 落库静默跳过，
   消息永远卡在 GENERATING。修法：写库失败时 `persisted.set(false)` 归还占位后 rethrow。
2. **GENERATING 无兜底**：进程重启/被杀时正在生成的消息没有任何终态落库机会
   （complete/fail/stop 与 doOnCancel 都随 JVM 消失）——这比"DB 写失败"常见得多，
   是"卡 GENERATING"的主要真实来源。修法：启动清扫
   `GeneratingMessageSweepRunner` → `ChatTransactionService.sweepStaleGenerating(cutoff)`
   → `MessageRepository.markStatusBefore`（JPQL 批量更新），把启动时刻之前创建的
   GENERATING 消息批量置为 ERROR，内容原样保留。

### 取舍
- 不新增 PERSIST_FAILED 状态：三态够用，"模型成功但保存失败"无需在 DB 层区分。
- 不引入任务存储：DB 就是唯一持久存储，DB 挂了整个应用都不可用。
- 评审建议要先问"触发概率 × 后果 × 修复成本"，落库失败概率极低，
  但同一后果（卡 GENERATING）的进程重启场景概率高，清扫一个机制同时覆盖两者。

## 评审意见核查：三条不成立 + 两个未来前置条件（2026-11-03）

### 核查结论（针对聊天流终态处理的评审）
1. "缺少独立 fail()/stop() 事务方法" —— 不成立。`ChatTransactionService.complete/fail/stop`
   本来就是独立 @Transactional 方法，`MessageService.persistTerminal` 只是内存分发器。
2. "点击停止不触发 doOnCancel" —— 不成立。前端停止按钮调 `AbortController.abort()`
   （`web-pc/src/pages/aiAssistant/index.jsx`），主动断开 SSE 连接正是 doOnCancel 的
   触发源，服务端在下次写 chunk 时感知断连并落库 STOPPED。
3. "没有条件更新有竞态窗口" —— 当前不成立。每个 send() 有独立 `persisted` CAS，
   两次成功写库不可能都通过；跨流各有独立消息行。
4. "orElseThrow 抛 NoSuchElementException" —— 当前不可达。ConversationController
   只有 list/create，没有任何删除消息/会话的入口。

### 两个未来前置条件（加对应功能前必须先补配套）
- **加独立 HTTP stop 接口时**：它绕开流内 CAS，必须先给终态落库加条件更新
  `UPDATE ... WHERE status = GENERATING`，否则 STOPPED/COMPLETED 双写竞态成真。
- **加删除会话/消息接口时**：生成中途删除会让终态落库的 findById 打空，
  需改为"行不存在则 log + 跳过"（Conversation 已配 cascade ALL + orphanRemoval，
  删除接口一上线此场景即可达）。

### 方法论
评审意见要逐条对照自己的代码验证触发前提，不能照单全收：
很多"标准建议"针对的是别的代码形态或你不存在的功能路径。

## reasoning 增量归一的固有歧义（2026-11-03 核查）

`MessageService.reasoningDeltaOf` 用"chunk 是否以累积文本为前缀"区分累积/增量两种
provider 语义：是则取新增部分，否则整块当增量。已尽量最小实现，无需修改。

固有歧义（已知，不修）：增量语义下，若某 delta 恰好以全部已累积文本开头（只在累积
极短时可能，如 1-2 字符），会被误判为累计前缀而丢字。没有额外信息可区分两种语义，
当前启发式已接近最优；仅在实际 provider 观察到丢字/重复时再针对性处理。

（2026-11-05 更新：启发式已随"reasoning 统一按增量语义处理"整体移除，
见同日条目——当前唯一接入的 reasoningContent 本就是增量语义，归一逻辑是用不到的防御。）

## ChatStreamEvent 事件类型：枚举而非字符串/常量（2026-11-03）

### 背景
SSE 统一事件协议的 `eventType` 最初是裸 String，5 个构造点散布在 `MessageService` 写字面量，
协议全集只存在于 javadoc；且 eventType 与 eventData 的配对（start→StartData、content→String…）
靠人肉保证。阶段 4 协议要从 5 种扩到 9 种（agent/tool_call/tool_result/usage），配对错误风险会放大。

### 决策
- 事件类型定为 `ChatStreamEvent.Type` 枚举，不用静态常量——常量方案的字段类型仍是 String，
  拦不住协议外取值，也无法表达「类型↔载荷」配对约束。枚举的封闭性在这里是优点：
  后端是协议唯一定义方且只序列化不反序列化，前端 JS 只消费字符串
- 每个枚举常量**显式声明 wireName**（不从枚举名 toLowerCase 推导），避免重命名常量时静默改协议；
  `@JsonValue` 让 JSON 内 eventType 输出 wireName；SSE event: 字段用 `event.eventType().wireName()`
- 构造收敛到每类型工厂方法（`ChatStreamEvent.content(...)` 等），编译期保证配对；
  record 紧凑构造器按 `payloadType` 再兜底校验一次，防止绕过工厂的直接构造
- 前端镜像常量对象 `ChatEventType`（`src/api/message.js`）消除 switch 裸字符串，后端枚举仍是事实来源

### Jackson 3 注意点
Spring Boot 4 用 Jackson 3（包 `tools.jackson`），但注解仍在
`com.fasterxml.jackson.core:jackson-annotations`（2.x 制品，databind pom 注释明确
"Annotations remain at Jackson 2.x group id"），`@JsonValue` 等 import 照旧。

## LLM 流式输出：类型驱动分发，不假设"先思考后正文"（2026-11-03）

### 背景
服务商流式输出的思考（reasoning）与正文（content）有两种模式：先思考后正文、两者交叉出现
（正文后可能再次出现思考），取决于模型机制与服务商协议。处理侧**不能**按"已出现正文则
后续全是正文"的顺序假设——事件类型必须由 chunk payload 结构决定。

### 落地（MessageService.send 的 modelEvents 管线）
- 两段式管线：`flatMapIterable(toDeltas)` 把 chunk 纯转换为有序增量列表（保序、无协议细节），
  `.map` 内模式匹配 switch 按类型分发（累积缓冲 + 生成 ChatStreamEvent）
- 增量用 sealed 接口 `ChunkDelta`（Reasoning/Content）限定全集，switch 不留 default、
  编译器强制穷尽；阶段 4 加工具调用时新增 permitted 子类型，所有分发点编译报错提醒
- 累积缓冲随分发分支回写（而非转换时）：保证缓冲内容 == 已发出事件内容，
  cancel/error 终态落库不会多出未发出的半截增量
- reasoning 的累计前缀归一仍留在转换侧（reasoningDeltaOf），只有转换侧关心上游语义差异

## finishReason 捕获：截断可见性与 metadata 的读取时机（2026-11-04）

### 背景
finish 事件的 `finishReason` 曾写死 "stop"。`LlmClientFactory` 未设 maxTokens（走服务商默认
输出上限，DashScope 部分模型默认仅 2048 token 左右），长回复被截断（finish_reason=length）
时用户看到残缺回复却无任何提示——静默错误。

### 方案与要点
- 流式协议里 **finishReason 只有最后一个 chunk 非 null**（中间恒 null），用
  `AtomicReference<String>`（默认 "stop" 兜底 provider 不上报的情况）在 `toDeltas` 里
  非空即覆盖，流结束时即为最终原因，随 finish 事件带出
- **读取时机坑**：finishReason 挂在 `result.metadata` 上、与 `result.output` 无关，
  必须在 output 判空早退之前捕获，否则末 chunk（可能只有 metadata 没有正文）的原因会丢
- 前端收到 finish 且 `finishReason === 'length'` 时 toast 提醒，不落库——截断是当次
  生成的即时反馈，为它在 Message 加字段收益不匹配（以后要加也是 nullable 列，向后兼容容易）
- 【2026-11-09 更正】曾以为可复用该通道捕获 `finish_reason = "tool_calls"` 来发工具
  观测事件，查 Spring AI 2.0 官方文档后确认不成立：`ChatClient.tools()` 自动注册的
  `ToolCallingAdvisor` 会递归执行工具并过滤掉工具调用块，下游末帧是 `stop`，拿不到
  工具轮。要观测工具调用需另注册观察 advisor，不是补一行映射就能做到。

## 协议预留 ≠ 提前发送：phase(model_request) 事件的撤下（2026-11-04）

### 背景
`ChatStreamEvent` 曾实现 `phase(model_request)` 事件为阶段 4（Agent 路由/工具调用）
预热协议。但它与 start 在订阅时同一个同步 drain 里背靠背发出（`Flux.just(start)
.concatWith(phase)`），中间没有任何实际工作——时序与内容完全被 start 决定，信息量为零。
副作用：前端收到 start 置 `waiting`、下一帧被 `request` 覆盖，`waiting` 标签成了
用户永远看不到的死状态。

### 结论
- **阶段/进度类事件必须携带超出已有事件的时序或信息增量**，否则只是噪音；
  "预留协议形状"靠保留枚举类型与工厂方法（当时保留 PHASE/PhaseData 并注释标明预留）
  就够了，不需要靠发送占位事件来"演习"管线。
- 等路由/工具调用上线、流程中出现真正的中途阶段（如 route_start）时恢复发送，
  协议结构不变。
- 前端派生状态（waiting/thinking/generating）改由 start/reasoning/content 事件
  直接推导，每个状态都可达。

### 后续（2026-11-10）：预留链彻底删除

上面说的「恢复发送」一直没有发生：意图路由随固定会话改造删除，`route_start` 不再存在；
工具调用虽已接入，Agent 层却没有中途阶段观测事件。PHASE 长期是「枚举里一个永远
不会被发出的值」，前端也早在 2026-11-05 删掉了 phase 状态条。本次删掉整条预留链：
`ChatEventType.PHASE`、`ChatEventFactory.phase()`、`payload/PhaseData`、
`AgentEvent.Phase`、`ChatEventConverter` 的对应分支、前端 `ChatEventType.PHASE` 常量。

结论修正：**协议形状不需要靠保留死枚举来预留**。将来真要加进度事件，按
「加常量 + 加 record + 加工厂方法 + 补 sealed 分支 + 前端补 case」一次做完即可
（见 `docs/编程规范/分层数据契约与协议隔离.md` 第 8 节），已发出的 SSE 帧不受影响。

## 流式管线按职责拆类 + reasoning 统一按增量处理（2026-11-05）

### 背景
外部评审发现 send() 散落状态有跨线程可见性竞争（chunk 在 Netty event loop 追加，
取消时落库快照在 boundedElastic 读取，无 happens-before，取消瞬间可能丢尾部内容），
并建议按职责拆类；同时决定 reasoning 不再做累计/增量归一——当前唯一接入
（Spring AI OpenAI 兼容 → DashScope）的 reasoningContent 本来就是增量语义，
"以累积文本为前缀"的启发式是用不到的防御且有固有歧义，整体移除。
此前"阶段 4 才是抽取流作用域状态对象时机"的记录因这个竞争提前。

### 最终结构（chat 包平铺，不引入子包）
- `ChatResponseParser`（静态工具类，包私有）：ChatResponse → ParsedChatChunk
  原始字段快照；Spring AI 对象结构知识只在这一个类。finishReason 仍先于 output
  判空提取（末 chunk 可能只有 metadata 没有正文）。
- `ChatResponseProcessor`（静态工具类，包私有）：chunk → ProcessedChatChunk
  （0~2 个有序 ChatDelta + finishReason），类型化 + 非空过滤，先思考后正文。
- `ChatDelta`（sealed interface）：内部统一增量类型（Reasoning/Content），
  分发点 switch 不留 default 的编译器强制不变。
- `ChatStreamEventMapper`（每次生成 new 一个）：ChatDelta → ChatStreamEvent；
  缓冲仍随分发分支回写（"缓冲内容 == 已发出事件"的不变量不变）。
- `GenerationState`（每次生成 new 一个）：内容缓冲/seq/finishReason/终态占位；
  content/reasoning/finishReason 读写走同一把锁（落库快照成对拷出），
  seq/persisted 无跨字段不变量、保留原子类。
- `MessageService` 只保留编排：initialize → 管线（process → 写 finishReason →
  concatMapIterable 保序摊平 → map 分发）→ 三条终态路径。

### 约定
- 将来接入累计式输出（cumulative）的服务商：按服务商声明的语义在 processor
  之前加 Normalizer，不要恢复前缀启发式。
- 无状态纯转换（Parser/Processor）→ 静态工具类（private 构造器），不经 Spring，
  方法引用 `ChatResponseProcessor::process` 直接用；携带每次生成状态的
  （Mapper/GenerationState）才保持实例——改静态只会让参数重新拖进签名。

## chat 流式管线全景与 content 双责任分离任务（2026-11-10）

### 管线全景（改这块代码前先看）

一次发送的完整链路，五段各有单一职责：

1. **入口装配** `MessageService.send()`：白名单校验 → 取 LLM 配置 → 阶段一初始化 → 组装 Agent 上下文。无事务注解，只在请求线程跑。
2. **阶段一初始化** `ChatTransactionService.initialize()`（独立短事务）：落 USER 消息 + GENERATING 占位 assistant 消息（拿 messageId）→ 加载全量历史转 `ChatHistoryMessage` DTO（排除 GENERATING 占位，空 content 会被 OpenAI 兼容端点 400 拒绝）→ 事务提交后才返回。
3. **Agent 执行** `AbstractLlmAgent.stream()`：system prompt + 历史 messages → Spring AI 流式调用 → `ChatResponseProcessor` 把厂商 chunk 归一为 `AgentEvent`（sealed：Content/Reasoning/FinishReason）。工具经 `tools(context)` 每次执行新建（绑定 userId，不能缓存——流管线线程没有 ThreadLocal）。
4. **流式编排** `GenerationPipeline.run()`：start → `ChatEventConverter`（AgentEvent→ChatEvent 纯转换，无状态）→ `MessageDraft` 缓冲 → 终态落库（boundedElastic）→ finish。error/cancel 两条旁路各落 ERROR/STOPPED。
5. **终态落库** `ChatTransactionService.complete/fail/stop()`：各自独立短事务，更新（而非新增）GENERATING 占位行。

### 三条铁律（改动时不能破坏）

- **缓冲 == 已发出事件**：`MessageDraft.append` 挂在「已转换出的 ChatEvent 流」的 doOnNext 上，不是转换器内部。cancel/error 落库的内容严格等于前端已收到的内容，不会多出未发出的半截增量。
- **唯一终态**：一次生成只允许 COMPLETED/ERROR/STOPPED 之一，`TerminalFinalizer` 的 CAS 保证；finish 事件在落库提交后才发，前端收到即可安全刷新。
- **模型生成不持有事务**：阶段一/阶段三都是独立短事务，中间流式生成不碰库。新增写库操作必须遵守这个结构，别把写库挂进流里。

### content 双责任问题（本次任务）

`Message.content` 目前一份字节四个消费者：模型写 → 前端流式收 → 落库 → 下一轮模型读回。
插入自定义内容（表单/图表）后三个具体问题：① 结构化数据混在 content 里下一轮全量回灌
烧 token 且诱导模型编造；② 图表数字若模型手写可能写错，正确来源是工具调用结果；
③ ERROR/STOPPED 半截态可能停在 JSON 标记写一半的位置。

### 已定方向（2026-11-10 确认）

- **一步到位做块协议**：不做"文本内嵌标记"过渡版。`AgentEvent` 加 Block 类型 →
  `ChatEventType` 加常量 → payload record → converter 分支 → 前端 case
  （新增事件的标准四步，见 `ChatEventType` 注释）。
- **图表数据来自工具调用**：工具返回的数据后端直接包成块，不经过模型逐字输出，
  保证数字准确、省输出 token；模型只写解读文字。
- **表单提交直接触发记账动作**：表单块有自己的提交通道，不走"提交=发一条 user 消息"。
- **待决：历史回读口径**——下一轮模型读历史时，块以什么形态出现在模型输入里
  （只读 content 原文 / content+块摘要 / 块完整数据），实施前需先定。

## 未落地的领域事件清理（2026-11-10）

`AgentEvent` 曾定义 `Artifact` / `ToolCall` / `ToolResult` 三个 record，`ChatEventConverter`
为它们各留一个恒抛 `UnsupportedAgentEventException` 的分支，作为 P2 卡片/工具观测的
