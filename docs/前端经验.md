# 经验：源码阅读笔记（umi / antd / 工程工具）

## 32. axios 数组参数会序列化成 `key[]=`，Spring 绑不上 List（2026-10-12）

> 由「moneyFlow 账单多条件查询」沉淀。

- **现象/根因**：umi 的 `request()` 底层是 axios，默认把数组 query 参数序列化成
  `categoryIds[]=1&categoryIds[]=2`；Spring 控制器用普通 POJO 绑定收 `List<Long>` 会绑不上
  （需要 `@RequestParam("categoryIds[]")` 或自定 serialization 才能接）。
- **解法（已落地）**：多选筛选参数统一改成**逗号分隔字符串**传参——前端 `buildQuery` 里
  `ids.join(',')`，后端 QueryForm 字段用 `String` 再自行 split 成 `List<Long>`。
- **通用经验**：凡 axios 传数组 query 参数给 Spring，都得先过「会不会变 `key[]=`」这一关；
  要么 `.join(',')` 传字符串，要么在 request 层配 `paramsSerializer`。项目里选了前者（零配置、两端对称简单）。
- 关联补充：后端 `parseIds(csv)` 忽略空/非法项，见 `docs/后端经验.md` 的 MoneyFlow 查询节。

## 33. 账户下拉需要合并 4 个 type 的 accountApi.list（2026-10-12）

> 由「moneyFlow 查询页账户筛选下拉」沉淀。

- `accountApi.list` 要按 `type`(1-4) 分次请求，单个 type 拿不全所有账户。账单筛选下拉要「全部类型」，
  用 `Promise.all([1,2,3,4].map(type => accountApi.list({ type, page:0, size:1000 })))` 后
  `flatMap(p => p?.content || [])` 合并成一份。
- 否则下拉里要么只有活期账户、要么选了对方账户却匹配不到——账单的「账户」语义是「转出或转入任一」，
  必须跨 type 全量。

## 34. 统计条与列表同条件：一个 query state + refreshDeps 自动联动（2026-10-12）

> 由「moneyFlow 每查一次同步输出 总支出/总收入/总结余」沉淀。

- 列表「搜索/重置」只改一个 `query` state（`setQuery(buildQuery(表单值))`），
  列表 `request` 展开 `...query` 触发请求（配合 `actionRef.reload()`），
  统计条 `useRequest(() => moneyFlowApi.statistics(query), { refreshDeps: [query] })` 随同一 `query` 自动刷新。
- 前端只序列化表单 → 一份 `query`，列表与统计永不偏离；不要给统计条单独再维护一份触发条件。

## 35. antd TreeSelect 默认 SHOW_CHILD 恰好实现「含子节点」（2026-10-12）

> 由「moneyFlow 分类筛选含子节点」沉淀。

- 需要「勾父分类 = 传该父及所有后代分类 id」时，`TreeSelect` 加 `treeCheckable` 且**不手写
  `showCheckedStrategy`** 即可：默认值就是 `SHOW_CHILD`，勾选父节点时 `value` 里是全部叶子 id。
- 所以「含子节点」语义无需前端展开树或后端递归：前端勾父→拿叶 id 数组→`.join(',')` 传后端，
  后端按 id in (...) 过滤，天然覆盖所有后代。
- 注意方向别搞反：如果后端想收叶子、前端却用 `SHOW_PARENT`，会漏掉深层分类。

> 由「old 项目登录成功后立刻被踢回登录页」bug 沉淀（后端日志：`user.authentication.invalid`）。

- **现象**：登录接口报成功，但很快弹回登录页。后端 `AuthInterceptor` 校验 JWT 抛 `user.authentication.invalid`。
- **根因**：登录页写了 `localStorage.setItem('accessToken', response.data)`，但这里 `response.data` 是 `LoginResponse` **对象**（`{accessToken, username, remember}`），不是 JWT 字符串。`localStorage.setItem` 传对象会被 `String()` 强转成 `"[object Object]"`，于是后续请求的 header 变成 `Authorization: Bearer [object Object]`，后端校验必然失败。
- **关键事实**：umi（`@umijs/max`）的 `request()` 默认返回 **`res.data`（响应体）**，不是完整 axios response——证据是生成的 `.umi/plugin-request/request.ts` 里 `resolve(getResponse ? res : res.data)`，`getResponse` 默认 false。所以后端 `DataResponse<T>` 返回 `{ success, data, message, showType }`，前端拿到的是整个 body，业务数据在 `res.data`，登录 token 是 `res.data.accessToken`。
- **修复**：`localStorage.setItem('accessToken', response.data.accessToken)`。
- **通用经验**：
  1. 用 umi `request()` 前先默认「返回值 = 响应体」，需要完整 response 时要 `{ getResponse: true }`。
  2. `localStorage.setItem(key, obj)` 会静默存成 `"[object Object]"`，存之前确保值是字符串（要用 `obj.accessToken` 而不是 `obj`）。
  3. 登录成功后 `Authorization` header 要用「请求拦截器里每次读 token」或「整页 reload 重新求值 config」——不要指望静态 header 对象在 SPA 内自动更新（本例靠 `window.location.href='/'` 整页重载才生效）。

## 30. 提示后立即整页跳转会丢失 toast，跳转要延迟（2026-10-10）

> 由「注册成功无提示直接跳登录页」bug 沉淀。

- **现象**：注册页 `handleSubmit` 里 `message.success(...)` 后紧跟 `window.location.href = '/login'`，用户看不到"注册成功，请登录"，直接进了登录页。
- **根因**：antd `message` toast 渲染在当前页面，`window.location.href` 是**整页跳转**，会立刻卸载当前页 DOM，toast 还没展示（最多闪一下）就被销毁。
- **修复**：跳转前给一段延迟，让提示先落地：
  ```js
  message.success(t('pages.register.success'));
  setTimeout(() => { window.location.href = '/login'; }, 1500);
  ```
- **通用经验**：任何「先提示、再整页跳转」的流程都要让提示落地再跳，否则提示形同虚设。若跳转是 SPA 内 `history.push`（不整页卸载），message 通常能保留，不受此影响。
- **对比**：登录页也是同一模式，但登录成功要尽快进 `/home`，不宜加延迟，属另一种取舍（要么接受 toast 一闪而过，要么在落地页另做提示），不能照搬注册页的延时写法。

## 29. 同一组件按不同 props 渲染多个视图要加 key，否则 props 变化不会重载（2026-10-05）

> 由「bookConfig 去掉 category 薄包装后切 tab 不刷新」bug 沉淀。

- **现象**：把 `ExpenseCategory`/`IncomeCategory` 两个薄包装删掉、统一成 `<CategoryTree type={1|2} />` 后，切换「支出/收入」分类 tab，列表不刷新、仍显示上一次的数据。
- **根因**：两个 case 现在返回**同类型、同位置**的组件，React diff 会复用同一个 `CategoryTree` 实例，只更新 `type` prop，**不会 remount**；而 `CategoryTree` 的 ProTable `request` 用闭包捕获 `type`（不是 `params`、也没 `refreshDeps`），`type` 变化不会触发重新请求。之前用两个不同组件类型（`ExpenseCategory` vs `IncomeCategory`）时，切换天然 unmount/mount，所以正常。
- **修复**：`<CategoryTree key={TAB_EXPENSE} type={...} />`，用 `key` 区分不同 tab，强制切换时 remount 重建。
- **通用经验**：判断「props 变化会不会触发组件内部重载」，只看内部**怎么消费** props——闭包捕获的 props 变化不会自动 reload，只有 `params` / `refreshDeps` / `useEffect deps` 才会。给「同类型、多实例、仅 props 不同」的列表加 `key` 是最省事的强制 remount 手段，别靠 React 复用去期待它自己重载数据。

## 28. 弹窗表单不要传外部 form：外部实例常驻会让 destroyOnHidden 失效（2026-10-05）

> 由「category 新增会带出上一条数据」bug 沉淀。

- **根因**：`BaseModalForm` 默认 `destroyOnHidden:true` 只在关闭时卸载 ModalForm 内部的 DOM/Form，**清不掉外部 `Form.useForm()` 创建的实例 store**。`CategoryForm` 此前在组件里 `const [form] = Form.useForm()` 又 `form={form}` 传进去，而它本身常驻渲染，form 实例始终存活——编辑后 store 残留，再点新增 name/notes 就是上一条的值。
- **原因链条**：`initialValues` 只在 Form 首次初始化时写入 store；store 一旦初始化过，再次打开不会重新应用 initialValues（这正是 §16 说「用 initialValues」、§10 说「destroyOnHidden 只清 DOM 不清数据」的同一件事）。
- **正例**：`currency/ActionForm.jsx`、`CategoryForm.jsx` 都不传 `form`，回显全靠 `initialValues` prop 交给 `destroyOnHidden` 每次重建，这是项目统一规范。
- **例外**：只有 `Form.useWatch('xx', form)` 这类必须显式拿 form 实例的场景才传 form（见 §10），那种情况必须额外配「打开时 useEffect 重置」，否则同样残留。
- **自查**：写 ActionForm 时若出现 `Form.useForm()`，先问自己是不是真的需要 form 实例；不需要就删掉，别顺手传 `form={form}`。

## 27. ProFormDatePicker 提交的是「字符串」不是 dayjs（2026-09-30）

- ProFormDatePicker 默认 `dateFormatter='string'`（`BaseForm.js` 里 `_props$dateFormatter ?? 'string'`），
  所以 onFinish 拿到的 `values.executeDate` 是 `"YYYY-MM-DD"` 这样的字符串，**不是 dayjs 对象**。
- **反例**：`values.executeDate.startOf('day').valueOf()` —— 字符串没有 `.startOf`，直接 TypeError，
  async onFinish reject 又被 ProForm 吞掉（见 §8），表现为「点确定没任何反应」。
- **正例**：提交时先转回 dayjs 再取时间戳：`dayjs(values.executeDate).startOf('day').valueOf()`。
- 回显方向（`initialValues`）反着来：`dayjs(row.executeDate)` 传 dayjs 给 DatePicker 才能正确展示，
  不要传字符串。
- 判断依据：`pro-utils/es/conversionMomentValue` 里 `dateFormatterMap.date = 'YYYY-MM-DD'`，
  `dateFormatter === 'string'` 时走 `value.format(...)` 转字符串。

## 26. 列表里「就地 Switch 保存」要用本地乐观态，别直接用 dataIndex 受控（2026-09-25）

- **反例**：`valueType: 'switch'` 在非 editable 的 ProTable 里是**只读**展示，点不动；
  即便改成 `render: (_, r) => <Switch checked={r.canExpense} />`，因为 `r.canExpense` 不随点击变化，
  受控 Switch 会「点了没反应」。
- **正例**：抽一个 `<EditableSwitch value onChange>`，内部 `useState(value)` 存本地态，
  `useEffect` 随 `value` 同步；onChange 先乐观 `setChecked(next)`，`await onChange(next)`
  成功后由 `actionRef.reload()` 拉回服务端真值，失败 catch 里 `setChecked(value)` 回滚
  （失败提示由全局 errorHandler 出，不用重复 toast）。该组件已抽取为共享组件
  `components/EditableSwitch`，直接 import 复用即可。
- **后端配套**：这种「只改一个字段」的局部 PATCH，UpdateForm 的 name 必须可空，
  否则 `@ValidName`（内含 `@NotBlank`）会拦下缺 name 的请求。可空写法对齐 `AccountUpdateForm`
  的 `@Size(max = 64)`。

## 25. render 函数里的动态文案也必须走 t()，别拼中文字面量（2026-09-25）

- **反例**：account 的账单日列 `render: (_, record) => \`${record.billDay}日\``——
  英文界面直接显示"10日"。这类"数字 + 单位/后缀"的动态拼接是最容易漏 i18n 的地方。
- **正例**：词条带占位符 `account.fields.billDay.value: '{day}日' / '{day}'`，
  render 里 `t('account.fields.billDay.value', { day: record.billDay })`。
- 排查方法：grep `src/pages` 里 JSX/模板字符串中的中文字符（不含注释和 t() 参数）。

## 24. sorter: true 需要 BaseProTable 转换 sort 参数才真的生效（2026-09-25）

- ProTable 的排序参数通过 `request(params, sort, filter)` 的**第二个参数**传入，
  不在 params 里。`BaseProTable` 的 wrappedRequest 目前只转换了分页
  （current/pageSize → page/size），`sort` 对象被直接丢弃。
- 后果：列上写 `sorter: true` + `defaultSortOrder: 'ascend'`，点表头切降序后
  数据仍是后端兜底排序（如 executeDate asc）——排序箭头是假的，属于 §21
  反对的"误导性排序暗示"的另一种形式（reminder 页面踩过）。
- 两个修法选一：
  1. 在 BaseProTable 转换边界把 sort 转成 Spring Pageable 方言
     `sort=field,asc|desc` 透传（它自称"唯一转换边界"，职责上应在此修，全项目生效）；
  2. 后端不支持排序的列不开 `sorter`，删掉 `sorter: true` / `defaultSortOrder`。

## 22. 请求返回值统一为 body.data，不要混用两种结构（2026-09-25）

- `src/api/request.js` 在统一出口解包（`body => body?.data`），`config/config.js` 配了
  `request.dataField: ''` 关掉 `useRequest` 的默认二次解包（`formatResult: result => result?.data`）。
- 因此 **任何时候都不要** 对 API 返回值再写 `.data` / `.success` / `.message`：
  - 直接 `await xxxApi.fn()` → 拿到的就是业务数据；
  - `useRequest(xxxApi.fn)` 的 `data` → 同一个业务数据。
- 写新 API 函数时直接 `return request(...)`，不要自己再解包。
- 反面教材（历史 bug）：`CategoryForm` 里 `useRequest(categoryApi.tree)` 拿到的已是数组，
  又写了 `optionsData?.data || []`，导致父分类下拉永远为空。
- 分页接口的 body.data 是 `{ content, current, pageSize, total }`（后端 PageResponse
  把分页元信息放在 data 内部，保证解包约定无例外，见 §23）。
- 如果未来某个接口确实需要响应头或外层字段，给该调用单独加 `getResponse: true`
  并在 `src/api/request.js` 里特判绕过解包——先讨论再改。
- `request.dataField` 是构建期配置，改 `config/config.js` 后必须重启 dev server，
  `.umi/plugin-request/request.ts` 才会重新生成，否则行为不变。

## 23. 分页契约：转换只在 BaseProTable 边界（2026-09-25）

> 由「修复分页转换不一致」任务沉淀（思路三：约定大于配置）。

- **请求方向**：API 层直接说后端方言 `page`（0 起）/ `size`，
  `crud.js` 的 list 是纯透传；antd 的 `current`（1 起）/ `pageSize` 只在
  `BaseProTable` 的 request 包装里转换。自定义分页接口零样板，不会再漏转换。
- **响应方向**：后端 `PageResponse` 的 data 是 `{ content, current, pageSize, total }`，
  `BaseProTable` 映射成 ProTable 的 `{ data, total, success }`。
- **页面 request 函数可返回两种结构**：后端分页结构（自动映射）或 ProTable 结构
  （空态短路、非分页树形列表，原样透传）。判据是返回值里有没有 `content` 数组。
- 教训：上一轮统一解包（§22）后，`total` 等顶层平铺字段被丢掉导致分页器失效——
  这就是把后端 PageResponse 改成 data 内嵌套的直接原因。契约设计要保证
  「data 就是全部业务载荷」，不要把业务字段平铺到 success 旁边。

## 19. 颜色一律用 antd token，不要硬编码十六进制（2026-09-24）

**反例**：提醒事项列表里直接写 `style={{ color: '#ff4d4f' }}`、`'#52c41a'`、`'#999'`。

**正例**：组件里 `const { token } = theme.useToken()`，颜色用 `token.colorError` /
`token.colorWarning` / `token.colorSuccess` / `token.colorTextDisabled` 等语义化 token。

**原因**：
- 换肤（暗色模式等）时硬编码色值不会跟着变，界面会出现违和色块。
- antd 设计 token 是统一的视觉规范入口，跟着 token 走自动获得设计系统的一致性。
- 项目规范明确"antd-style 负责组件级动态样式，围绕 antd token 定制"。

**适用场景**：所有组件内联样式里的颜色（成功/警告/错误/禁用文本等）。
如果是组件级复杂样式，用 `createStyles` 写样式文件更整洁。

## 20. useModalForm 扩展 showCopy 模式（2026-09-24）

**背景**：提醒事项页面加了"复制"功能，沿用以现有 `useModalForm` hook 为基础，
新增 `showCopy(row)` 方法。

**模式语义**：
- `add`：纯新增，`currentRow = undefined`，`isEdit = false`
- `copy`：复制新增，`currentRow = 原记录`，`isEdit = false`，走 create 接口
- `edit`：编辑，`currentRow = 原记录`，`isEdit = true`，走 update 接口

**ActionForm 注意事项**：
- 复制模式下 `initialValues` **不能直接展开 `...currentRow`**，要手动挑表单需要的字段，
  否则 `id` / `completed` 等后端字段会被带进表单（虽然 create 接口大概率忽略，但不严谨）。
- 标题仍显示"新增"（`isEdit ? '编辑' : '新增'`），复制和新增共用 create 分支。
- `isCopy` 标志位保留给需要区分"复制 vs 纯新增"的场景（如复制提示文案）。

## 21. ProTable 排序：用 sorter 属性，别自己画装饰箭头（2026-09-24）

**反例**：在列 title 里手动放 `<ArrowUpOutlined />` 图标暗示"按此列升序"，但图标不可点击。

## 18. 受保护资源的判断逻辑放后端，前端不要硬编码（2026-09-23）

**反例**：币种管理的 USD/CNY 受保护，前后端都硬编码了 `code === 'USD' || code === 'CNY'`，
要改保护规则得同时改好几处，容易不一致。

前端直接用 `record.deletable` / record.rateEditable` 判断。保护规则只有后端一处说了算。

**适用场景**：任何有"系统内置/受保护/不可操作"概念的资源（币种、默认分类等）。

## 17. 树形结构的父级字段统一叫 parentId（2026-09-23）

**结论**：所有树形节点（分类、账户层级等）的父级 id 字段统一为 `parentId`，
前后端一致，不要再用 `pId`。

**背景**：早期 `TreeNode` 用 `@JsonProperty("pId")` 序列化为 `pId`（zTree 风格），
前端读 `record.parentId` 永远是 `undefined`，容易踩坑。已统一改成 `parentId`。

## 16. ModalForm 回显用 initialValues，别用 useEffect + setFieldsValue（2026-09-23）

**bug 场景**：弹窗表单打开时，部分字段（尤其是 Select 类）回显失败，
要么显示数字 id，要么直接空着。用了 `useEffect` 监听 `modal.open` 然后
`form.setFieldsValue()`，但时灵时不灵。

**原因**：`ModalForm` + `destroyOnHidden` 模式下，弹窗打开时表单字段
才开始注册到 Form 上。`useEffect` 在 `open` 变化时立即触发 `setFieldsValue`，
但此时 Form.Item 可能还没完全注册，值就丢了。文本框侥幸能显示是因为
后续渲染时还能捡到值，Select 类组件因为 options 映射时序问题就挂了。

**正确做法**：用 `ModalForm` / `BaseModalForm` 的 `initialValues` prop，
让组件内部在正确的时机设初始值。这是 pro-components 推荐的方式，
和 `destroyOnHidden` 配合最稳定。

参考样板：`src/pages/currency/ActionForm.jsx`。

## 15. ProTable 刷新：actionRef.reload 还是 useRequest.run（2026-09-23）

> 修复「新增分类后表格不刷新」的 bug 时沉淀。

**bug 场景**：组件里同时有 `useRequest` 返回的 `run`（命名为 `reload`）和
`BaseProTable` 的 `actionRef`，操作成功后调了 `reload()`，但表格纹丝不动。

**原因**：`useRequest` 的 `run` 刷新的是它自己管理的那份数据（`data`），
如果这份 `data` 根本没被表格消费（表格的数据来自 `request` prop，由
ProTable 内部自己管理），调了等于白调。

**正确做法**：
- 表格数据来自 ProTable 的 `request` prop → 用 `actionRef.current?.reload()` 刷新
- 组件自己 `useRequest` 拉的数据（如下拉选项等）→ 用它自己的 `run` / `refresh`
- **不要给没人消费的 useRequest 留着占位置**，直接删掉

顺手把 `actionRef = { current: null }` 的写法换成 `useRef(null)`，
前者每次 render 都新建对象（虽然 ProTable 只赋值一次、影响不大，但不规范）。

## 12. API 层 CRUD 复用：createCrudApi + pickCrudApi（2026-09-23）

> 由「api 目录架构优化」任务沉淀。

### 问题
`createCrudApi(prefix)` 一次性返回 5 个方法（create / list / options / update / delete），
像 `categoryApi` 这种只需要部分方法（create/update/delete）的接口，要么手写重复代码，
要么被迫接受多余的方法（list/options 实际上后端没有）。

### 解法：方法表 + 按需选取
把每个 CRUD 方法拆成独立的工厂函数，存在 `CRUD_METHODS` 表里。
- `createCrudApi(prefix)` — 全量拿（旧 API，完全兼容）
- `pickCrudApi(prefix, keys)` — 按数组选取需要的方法

```js
// src/api/crud.js
const CRUD_METHODS = {
  create: (prefix) => (data) => request(prefix, { method: 'POST', data }),
  list: (prefix) => (params) => { ... },
  options: (prefix) => () => request(`${prefix}/options`, { method: 'GET' }),
  update: (prefix) => (id, data) => request(`${prefix}/${id}`, { method: 'PATCH', data }),
  delete: (prefix) => (id) => request(`${prefix}/${id}`, { method: 'DELETE' }),
};
```

用法：
```js
// 全量
export const tagApi = { ...createCrudApi('/tags') };

// 部分 + 自定义方法
export const categoryApi = {
  ...pickCrudApi('/categories', ['create', 'update', 'delete']),
  tree: (type) => request(`/categories/tree`, { method: 'GET', params: { type } }),
  move: (id, data) => request(`/categories/${id}/move`, { method: 'PATCH', data }),
};
```

### 原则
- 纯 CRUD（5 个方法全用）→ `createCrudApi`
- 有自定义方法 + 不需要全部 CRUD → `pickCrudApi` + 手写自定义方法
- 完全非 CRUD 的接口（userApi 等）→ 手写，不用这套
- 方法表 `CRUD_METHODS` 是唯一事实来源，两种导出函数都从同一张表生成，逻辑零重复

## 11. 分类树形表格 + 弹窗表单（2026-09-20）

> 由「账本配置-支出/收入分类」任务沉淀。

### ProTable 树形数据
分类列表用 ProTable 展示树形结构，关键点：
- `childrenColumnName="children"` — 指定子节点字段名（后端返回的树结构就是 children）
- `expandable={{ defaultExpandAllRows: true }}` — 默认全部展开
- `pagination={false}` — 树形数据不分页
- `rowSelection={false}` — 不需要行选择
- `tableAlertRender={false}` — 关闭批量操作提示条
- `request` 返回 `{ data: treeData, success: true }`，ProTable 会自动处理 children 渲染

### 新增子分类的模式
不是在每行放独立弹窗，而是**共用一个弹窗 + parentNode state**：
- 点"新增一级分类" → `parentNode = null` → 弹窗 title 为"新增一级分类"，parentId 默认空
- 点某行"新增子分类" → `parentNode = record` → 弹窗 parentId 默认选中该行
- 编辑 → 不需要设置 parentNode，form 从 currentRow.parentId 回填

### 父级选择器的层级缩进
父级 select 的 options 从树结构扁平化生成，用全角空格 `'　'.repeat(level)` 缩进
表示层级关系。编辑时当前节点自身 **以及它的所有后代** 都要在 options 里 `disabled`：
自身防止选自己做父级，后代防止移动到自己的下级导致后端报 `error.category.parent.descendant`
（仅禁自身不够，后代也是后端会拒绝的非法父级，这是后来补的坑）。`allowClear` 允许清空 → 移动到根级。

### 编辑时移动父级：独立 move 接口
后端把"修改基本信息"和"移动父级"分成两个接口（PATCH `/{id}` 和 PATCH `/{id}/move`）。
前端编辑提交时：
1. 先调 update 改 name/notes
2. 再比较 `oldParentId !== newParentId`，有变化才调 move
这样避免了 PATCH 部分更新中"null 表示未传 vs null 表示根级"的歧义。

### 操作列按钮
树形表格操作列固定 3 个按钮：新增子分类 / 编辑 / 删除。
- 第 4 级的"新增子分类"按钮 `disabled`（受最大层级限制）
- 删除走 `modal.confirm` 二次确认（与 book/account 一致）

# 经验：源码阅读笔记（umi / antd / 工程工具）

## 1. umi 渲染管线：谁包谁（Provider 包裹顺序）

**结论：app.jsx 的 `rootContainer` 在所有插件 provider 之外（最外层），但在「插件通过 rootContainer 这个 key 注入的 wrapper」之内。**

推导三步（换版本后按此路径复核）：

1. **应用顺序**——后应用的 key 在外层。
   源：`node_modules/.pnpm/@umijs+renderer-react@<ver>_<hash>/node_modules/@umijs/renderer-react/dist/browser.js`

   ```js
   UMI_CLIENT_RENDER_REACT_PLUGIN_LIST = [
     'innerProvider', 'i18nProvider', 'accessProvider',
     'dataflowProvider', 'outerProvider', 'rootContainer',
   ];
   ```

   循环对每个 key 依次 `applyPlugins({ type: 'modify' })`，每个 hook 接收「目前累计包好的元素」再包一层。`rootContainer` 最后应用 → 最外层（再往外只剩 umi 自己的 `AppContext.Provider`）。

2. **同 key 多个 hook 的执行顺序**——先注册先执行。
   源：`node_modules/.pnpm/@umijs+core@<ver>/node_modules/@umijs/core/dist/service/service.js`
   modify 类型用 tapable 的 `AsyncSeriesWaterfallHook`：按 tap（注册）顺序执行，第一个 hook 收到 `initialValue`，后续 hook 收到上一个 hook 的返回值。

3. **注册顺序**——app.jsx 最先。
   源：生成代码 `src/.umi/core/plugin.ts` 的 `getPlugins()`，`Plugin_0 = src/app.jsx`，之后才是 core 插件、feature 插件（plugin-antd 等）。
   因此对 `rootContainer` 这个 key 的 waterfall：app.jsx 先执行（内层），插件的 rootContainer hook 后执行（外层）。

本项目最终树（实测）：

```text
AppContext.Provider（umi）
└─ AntdProvider      ← plugin-antd 的 rootContainer hook：ConfigProvider + AntdConfigContext
   └─ <App>          ← app.jsx rootContainer 自挂（AppBridge / OfflineBanner / ErrorBoundary 在内）
      └─ … outerProvider → dataflowProvider → accessProvider → i18nProvider …
         └─ <App>    ← plugin-antd 的 innerProvider（config 配了 antd.appConfig 才挂）
            └─ 路由 / 页面
```

写代码时的实际意义：

- 想包**全局最外层**，写 app.jsx 的 `rootContainer`。
- rootContainer 层拿不到插件 innerProvider 的 context：要用 antd 的 `App.useApp()` 必须自挂一层 `<App>`（嵌套是官方支持的用法）。
- rootContainer 层**在插件 ConfigProvider 内侧**（第 3 步的副作用），主题 token 不会丢。
- 页面组件的 `App.useApp()` 拿到的是 innerProvider 那层的实例；rootContainer 层组件拿到的是自挂那层的实例，两层互不干扰。
- plugin-antd 挂载点速查（`src/.umi/plugin-antd/runtime.tsx`）：`innerProvider` 挂 `<App {...appConfig}>`；`rootContainer` 挂 `AntdProvider`（ConfigProvider），并把 theme 同步给静态方法（`ConfigProvider.config({ theme })`）。

## 2. antd：静态方法警告与「实例桥」

- 警告：`Warning: [antd: message] Static function can not consume context like dynamic theme. Please use 'App' component instead.`（antd v6 仍有）。
- 根源：静态 `message` / `notification` / `Modal` 是模块级单例，读不到 React context（主题、locale、prefixCls）。
- 官方解法「实例桥」：组件里 `App.useApp()` 存进模块级变量，非组件代码（request 拦截器等）从模块变量取。
  本项目落地：`web-pc/src/utils/antdApp.js`（缓存）+ `web-pc/src/components/AppBridge/index.jsx`（无渲染桥接组件）+ `app.jsx` 的 rootContainer 自挂 `<App>`。
- 细节经验：
  - **render 期缓存实例优于 useEffect**：幂等副作用，且首帧前就可用；useEffect 会在挂载完成前留空窗，空窗期只能回落静态方法（警告重现）。
  - `<App>` 嵌套合法，每层渲染自己的 message holder，互不冲突。
  - 排查漏网的静态调用：先 grep `from 'antd'` 且含 message/Modal/notification 的 import，再 grep `message.(error|success|open|loading)`、`Modal.(confirm|info|...)` 调用点。

## 4. biome 使用要点

## 8. 登录错误处理收口：连空 catch 都不用（2026-08-29）

> 由「登录失败提示改用后端 message」任务沉淀。此前沿用 §7 旧口径给 login 加了 `skipErrorHandler` + 页面 catch 弹固定文案，本次改回全局 errorHandler；「ProForm 吞 rejection」的行为读 node_modules 源码验证过（版本基准 @ant-design/pro-components 3.1.14-2）。

- **改动**：`userApi.login` 去掉 `skipErrorHandler`；`pages/user/login/index.jsx` 的 `handleSubmit` 删除整个 try/catch，只留成功路径。`pages.login.failure` 词条（zh/en）已删，全仓库无残留引用。
- **效果**：失败弹的是后端按请求 Locale 渲染好的 message（`InvalidCredentialsException` → BusinessException 兜底 422 → `GlobalExceptionHandler` → "用户名或密码错误"），全局 handler 非 401 分支直接展示 `data.message`；断网/超时/500 由全局 handler 给对应网络类提示，不再被页面统一误报成"请检查账号密码"；登录失败 422 不会误触发 `handle401` 重定向。
- **「不会有 unhandled promise rejection」的完整证据链**（此前只看到 request runtime 的 reject 就断定页面必须 catch，是错的）：
  1. umi request runtime 在执行完 errorHandler 后确实仍会 `reject(error)`（`src/.umi/plugin-request/request.ts` 的 request 函数 catch 块末尾）——「页面拿到的 promise 一定 reject」这半句没错。
  2. 但 rejection 会被页面 `await` 往上抛，最终由 **ProForm 的 onFinish 包装函数兜住**：`node_modules/@ant-design/pro-components/es/form/BaseForm/BaseForm.js`（约 366-397 行）——`propRest.onFinish(finalValues)` 返回的 thenable 在内层 `try { await response } catch { setLoading(false); throw error; }`，rethrow 再被外层 `catch (error) { setLoading(false); }` 吞掉，包装函数自身永远 resolve。
  3. LoginForm 对 onFinish 原样透传给 ProForm（`es/form/layouts/LoginForm/index.js`），此行为对 ProForm 系所有表单（LoginForm/ModalForm/DrawerForm/StepsForm…）成立。
- **升级注意**：「ProForm 吞掉 onFinish 的 rejection」是实现行为而非 API 契约，升级 pro-components 后按上面路径复核；若新版不再吞，页面再补 catch 即可。
- **已知权衡**：后端 message 语言跟随 Accept-Language（Spring `LocaleContextHolder`），前端 UI 语言跟随 umi locale（localStorage），二者理论上可能不一致；全站其他接口（含 register）本就如此，`docs/api-response-convention.md` 即此约定，非本次引入。

## 10. Account 列表页：Tabs 切换 + 顶部汇总条（2026-09-19）

> 由「完成 account 增删改查」任务沉淀。

### 布局模式：Tabs 替代搜索区

需求是「不需要搜索区域，但是表格的上方要有 tab，切换 account 的 type 显示」。
做法：在 `BaseProTable` 外面套一个 `Card`，里面放 `Tabs` + 汇总数据，
作为列表的顶部控制条。ProTable 本身的 `search={false}` 关闭搜索区。

Tabs 切换时：
1. `activeType` state 更新
2. ProTable 不会因为闭包变量变化自动 refetch，**必须手动调用 `actionRef.current?.reload()`**
   （在 `handleTabChange` 里）
3. 顶部汇总条的 `useRequest` 如果用 `refreshDeps` 依赖 activeType，自动刷新不可靠，
   建议直接在 `handleTabChange` 里手动 `runSummary(type)`

### 顶部汇总条：多 Statistic 布局

活期/资产类只有"总余额"1 个统计；信用卡/贷款类有 3 个统计（总余额、总额度、总可用额度）。
布局：`Tabs` 在上，下面用 `display: flex; gap: 32; flex-wrap: wrap` 排多个 `Statistic`。
- 余额为负时用红色（`#ff4d4f`）
- 可用额度用绿色（`#52c41a`）
- 数字格式化用自定义函数（去掉末尾无效零），不用 `Statistic` 自带的 `precision`

### ProTable render 函数的第一个参数不要信

ProTable / Table 的 `render(text, record, index)` 中，第一个 `text` 参数
经过了 ProTable 的空值处理（null/undefined 会变成 `-` 字符串）。
如果直接用 `Number(text)` 转换，`"-"` 会变成 `NaN`。
**安全做法：始终从 `record` 上读原始值**，render 的第一个参数只用于纯展示列。
本项目里 `renderMoney`、`renderBalance`、账单日、APR 列都踩过这个坑。

### ProFormDigit 负数输入变 0 的坑

`ProFormDigit`（antd v6 / pro-components v3）默认 `min=0`，输入负数失焦后会被截断为 0。
需要支持负数余额时，显式设 `min={-Infinity}`。

### 表单状态残留：destroyOnHidden 只清 DOM 不清数据

`ModalForm` 的 `destroyOnHidden` 只在关闭时卸载 DOM，不会重置 Form 实例数据。
如果 Form 实例是在父组件用 `Form.useForm()` 创建的，数据会一直保留在 form 实例上。
表现：点完编辑再点新增，表单里带着上一条记录的数据。

修复方案（推荐）：
- **不要传 `initialValues` prop**（它会和 resetFields 冲突）
- 用 `useEffect` 监听"弹窗打开"事件，根据 mode 分别处理：
  - add 模式：`form.resetFields()` 清空 + `form.setFieldsValue()` 设默认值
  - edit 模式：`form.setFieldsValue()` 回填当前行数据
- 弹窗关闭时 form 实例保留没关系，下次打开时 useEffect 会重置

### Form.useWatch 必须在 Form 组件上下文内

如果 `useWatch` 调用在 `Form` 组件外部（比如封装的 ActionForm 组件里，
`BaseModalForm` 内部才是 `<Form>`），`useWatch` 拿不到 form 实例，
type 切换时动态字段不会更新。

**解法**：在父组件用 `Form.useForm()` 创建 form 实例，把 form 传给
`BaseModalForm`（通过 `formProps={{ form }}` 或直接透传），然后
`Form.useWatch('type', form)` 显式传第二个参数 form，这样 useWatch 不依赖
Form context 也能工作。

### 余额双向换算（表单 ↔ 最小单位）

余额以"最小货币单位"存储（Long），表单里用户输入的是正常小数。
- 回填：`balance / 10^decimalPlaces` → 展示给用户
- 提交：`Math.round(input * 10^decimalPlaces)` → 转回最小单位 Long
- 币种切换后 decimalPlaces 变化，已输入的余额要重新换算（体验更好），
  或者在 onFinish 时用当前选中币种的 decimalPlaces 做转换
- 新增时余额默认空（不是 0），让用户有"没填"的感知

### 本位币换算显示

列表余额列：如果账户币种 ≠ 本位币，在原币种金额后面用浅色小字
（`color: rgba(0,0,0,0.45); fontSize: 12`）显示 `≈ 本位币金额`。
判断同币种：`balance === baseBalance && currencySymbol === baseCurrencySymbol`
（两个都判断，避免不同币种恰好数值相同的误判）。

### ActionForm 新增时默认 type 和默认币种

- **type 默认值**：从父组件传入（`defaultType` prop），即当前 Tabs 选中的 type。
  符合用户预期：在"信用卡"tab 点新增，默认就是信用卡类型。
- **币种默认值**：新增时选中用户的本位币（从 `userApi.getInitState()` 或
  `currencyApi.listOptions()` 里找 `isDefault`/`base` 标记的）。
- 编辑时用 `currentRow` 的值，type 和 currency 创建后都不可改（与 currency 模块一致）。

### 动态列：useMemo 基于 activeType 生成

不同 type 显示不同的列（信用卡有信用额度/账单日，贷款多一个年化利率）。
用 `useMemo(() => { const cols = [...baseColumns]; if (...) cols.splice(...); return cols; }, [activeType, t])`
在基础列数组中插入特定列，操作列最后 push。`splice(index, 0, item)` 插入到
指定位置（index 是插入后该元素的位置）。

### 列表内联 Switch 操作

"计入净资产"这种布尔字段，直接在表格列里渲染 `Switch size="small"`，
用户点击立即调用 update 接口，成功后 reload 表格 + 刷新汇总。
不需要弹窗确认，操作轻量。与删除操作（需要确认）形成对比。

### ProFormSwitch 在 horizontal 布局下的对齐

ProFormSwitch 的 label 对齐在 horizontal 布局里与 ProFormText 一致，
`labelCol={{ span: 8 }}` `wrapperCol={{ span: 16 }}` 够用。
多个 switch 并排时用 `<Row gutter={16}><Col span={12}>` 两列布局。

## 37. 表单「类型」字段：新增用 Tabs、编辑禁用只读（2026-10-13）

> 由「moneyFlow 账单弹窗类型输入项改 tab」沉淀，参考 old `BalanceFlow/ActionForm.jsx` 的做法。

- **需求**：新增弹窗里「类型」从下拉改成三个 tab（新增支出/收入/转账），编辑弹窗不显示 tab、类型不可改。
- **关键坑**：antd `Tabs` 不是受控表单控件——它用 `activeKey`/`onChange`，不是 `value`/`onChange`，
  直接塞进 `<Form.Item name="type">` 指望自动绑定是绑不上的。两个踩坑点：
  1. Form.Item 会往子组件注入 `value`、`onChange`，但 Tabs 只认 `activeKey`，自动绑定失效。
  2. 手写在 Tabs 上覆盖 `onChange` 会同时盖掉 Form.Item 注入的 onChange，字段值得自己写。
- **落地写法（最稳）**：真实值用隐藏字段承载，视觉控件单独渲染、手动同步：
  ```jsx
  <Form.Item name="type" hidden><Input /></Form.Item>   // 承载值，供 useWatch 和提交
  {isEdit ? (
    <Form.Item label={t('moneyFlow.fields.type')}>
      <Select disabled value={typeValue} options={typeOptions} />
    </Form.Item>
  ) : (
    <Tabs
      activeKey={typeValue ?? TYPE_EXPENSE}
      onChange={(v) => { form.setFieldValue('type', v); 清关联字段; }}
      items={FORM_TYPES.map((type) => ({ key: type, label: t('add') + t(getTypeLabelKey(type)) }))}
    />
  )}
  ```
- **默认值**：新增打开时在打开 effect 里 `form.setFieldsValue({ type: TYPE_EXPENSE })`，
  否则 `useWatch('type')` 首次为 undefined，Tabs 会无选中项。
- 编辑态虽然隐藏了 `name="type"` 的可编辑字段，但真实值仍在 `values.type`，提交逻辑零改动。
- **弹窗标题按类型动态，编辑态不再显示类型**：新增用 tab 当标题，顶部 title 传 `null`（tab 文案 `新增支出/收入/转账` 已够，不重复）；
  编辑态删掉「类型」禁用 Select、标题按记录类型拼 `修改{type}`（修改支出/修改收入/修改转账/修改余额调整），
  词条用占位符 `moneyFlow.action.editByType`（zh `修改{type}` / en `Edit {type}`），基于 `currentRow.type` 而非 `useWatch('type')` 计算（避开回填时序导致标题短暂为空）。

## 36. 流水表单多币种金额精度：amountDP / needConvert / targetDP 三件套（2026-10-13）

> 由「moneyFlow 新增/编辑弹窗 ActionForm」沉淀。跨币种时金额与折算金额各按自己币种的小数位取精度。

- **换算关系随 type 变，别用单一币种套**：
  - 金额（amount）币种 = 选了账户取账户币种，未选（未归属收/支）取账本币种 → `amountDP`。
  - 折算金额（convertedAmount）目标币种 = 转账取转入账户币种、收/支取账本币种 → `targetDP`。

- **转账没有账本币种这回事**：转账的折算目标是转入账户币种（不是账本币种），收/支的折算目标才是账本币种。

  `currentRow.currencyDecimalPlaces`（列表项该字段恒为账本币种小数位）；amount 精度统一用
  `currentRow.amountCurrencyDecimalPlaces`（列表项已带账户币种小数位，账户未归属时为账本币种）。
- **「当前账本币种小数位」没有现成前端接口**：`bookApi.list({page:0,size:1000})` 找 `isCurrent`
  → `currencyId`，再 `currencyApi.options()` 里按 `value` 匹配拿 `decimalPlaces`，两段串起来求
  `bookCurrency`（useMemo 保证引用稳定，避免 useEffect 反复触发）。没有像 account 的 CurrencyOption
  那样直接带 decimalPlaces 的选项接口，别再手写一套查币种。

## 40. 「下拉跟着所选账本走」的通用套路（2026-10-14）

> 由「moneyFlow 账单补账本：新增/查询换账本后，分类/标签/交易对象下拉要切到该账本」沉淀。

- 页面里 `Form.useWatch('bookId', form)` 取当前选中的账本，再用
  `effectiveBookId = bookId ?? currentBookId`（`currentBookId` 来自 `bookApi.list` 里 `isCurrent` 那条）
  得到「下拉该加载哪个账本」；下拉请求把 `bookId: effectiveBookId` 放进 `refreshDeps`，换账本自动重拉。
  空即回退当前账本，语义与后端「bookId 为空=当前账本」对齐。
- **换账本必须清掉旧账本的关联已选值**：`onChange` 里 `setFieldValue` 清 `categoryId/tagIds/payeeId`
  （账户是用户级、跨账本仍有效，不用清），否则残留上一账本的 id 提交后被后端 `findByIdAndBookId` 拒掉。
- **给已有 list 端点加可选 `bookId` 时，函数签名向后兼容**：`categoryApi.tree(type, bookId)` 里参数对象用
  条件展开 `{ type, ...(bookId != null ? { bookId } : {}) }`，老调用方 `tree(type)` 不受影响；
  对 `createCrudApi` 生成的 `tagApi.list/payeeApi.list` 无法改签名，就在调用处展开
  `list({ page:0, size:1000, ...(id != null ? { bookId: id } : {}) })`。
- **通用经验**：umi `request` 底层 axios，`params` 里塞 `undefined` 可能被序列化成 `key=undefined` 让 Spring
  绑 `Long` 报 400；「可选 query 参数」一律用条件展开 `...(v != null ? { k: v } : {})`，别直接传 `undefined`。

## 41. 搜索表单给过滤项一个「默认生效 + 可清空」的值（2026-10-14）

> 由「账单统计/列表默认排除 include=false 的流水（计入统计=是），用户可清空查看全部」沉淀。

- 需求形态：某布尔过滤项要**默认等于某值**（如 include 默认 true），但用户能 `allowClear` 清空回「不过滤」。
  实现时**三处必须一致**，否则「首次加载」和「点搜索/点重置」口径会漂移：
  1. `query` state 初始值：`useState({ include: true })` —— 决定首次加载时列表与统计用默认过滤；
  2. `Form.Item name="include" initialValue={true}` —— 决定表单下拉的默认选中态；
  3. `handleReset` 里 `setQuery({ include: true })`（配合 `form.resetFields()` 回 `initialValue`）—— 决定「重置回默认」。
- **为什么不能只设 `initialValue`**：`initialValue` 只管表单展示和 resetFields，`query` state 初始仍是 `{}`，
  首次加载不会带该过滤条件，出现「下拉明明选了 true，统计却算了全部」的表里不一。
- **与弹窗回显经验（§「表单状态残留」）的边界**：那条「不要传 initialValues prop、改用 useEffect+setFieldsValue」
  针对的是 *ModalForm 弹窗回显*（instance 常驻、打开要重新回填）；本条是 *常驻搜索表单*，恰恰要 `initialValue`
  让 `resetFields` 回到默认值，两者场景不同、不冲突。

## 42. 表单「打开回填」effect 别把 watch 派生值放进依赖（2026-10-14）

> 由「moneyFlow 新增账单：有两个账本时，选第二个会自动切回第一个」bug 沉淀。

- 现象：新增弹窗里切换账本，选中第二个瞬间弹回第一个（当前账本）。
- 根因：回填 effect 依赖数组里混进了 `bookCurrency`——它是一个 `useMemo`，依赖
  `effectiveBookId = Form.useWatch('bookId') ?? currentBookId`。用户切账本 → `bookId` 变 → `bookCurrency`
  重算 → effect 重跑 → 新增分支 `form.resetFields() + setFieldsValue({ bookId: currentBookId })` → 把账本又覆盖回默认值。
  本质是「初始化的 effect」被「用户自己的表单输入」再次触发，实现成了一次回退循环。
- 修复：**按分支拆分**两个 effect——编辑回填、新增填默认值各自独立。新增 effect 的依赖只留
  `[open, isEdit, form, currentBookId]`，**不含**任何随表单输入变化的派生值（`bookCurrency`/`effectiveBookId`），
  于是切账本不会再触发初始化。编辑态 `bookId` 禁改、`bookCurrency` 稳定，留在编辑 effect 依赖里无妨。
- **通用经验**：一个「仅应在弹窗打开/行切换时执行一次」的 effect，依赖数组里**不要放**由
  `Form.useWatch(<该 effect 要回填的字段>)` 派生的值（`useMemo`/`accountOptions` 等会随用户改动变化的量）。
  只要这类派生值进依赖，用户改那个字段就会重跑初始化、把值压回去。判断标准：依赖是否为「打开动作输入」的纯函数，
  是才算安全；「内部派生值随表单交互变化」的都不安全，应拆 effect 或改用 ref 记录「是否已初始化」的闸门。
- **必现 vs 不现，看派生值是「对象」还是「原始值」，别一刀切**：account 的同类 effect 依赖 `decimalPlaces`
  （`useMemo` 返回 number）却没复现——因为只有切换到「精度不同」的币种时数值 `2→0` 才变、才触发重跑；
  而 moneyFlow 的 `bookCurrency` 返回对象 `{ id, decimalPlaces }`，每次切换账本 `find` 出新引用，`Object.is`
  必判不相等 → **必重跑**。所以：派生值返回对象（`map/find` 新对象、`{}` 字面量、数组）进依赖几乎必踩坑；
  返回原始值（number/string/boolean）只是「条件踩坑」。排查时先看它返回的值类型，再决定是不是真 bug。

## 43. 列表 Tag 显眼：后端无 color 字段时用 antd 预设色按 id 稳定分配（2026-10-14）

> 由「账单列表标签默认灰色不够显眼」沉淀。

- 标签这类「后端没有颜色字段」的并列小件，要显眼 + 区分，别硬编码 hex（违反 §19），
  直接用 antd `Tag` 的 `color` 预设色名，按 `id % 色板长度` 取色：同一标签颜色稳定、相邻 id 颜色错开、零配置。
- 结局色板避开 `red`（与错误/支出等语义色撞），用
  `['blue','cyan','geekblue','purple','gold','orange','green','lime','volcano','magenta']`。
- 边界：这是「前端分配的展示色」，标签之间不保证全局唯一、用户不可配置。若将来要
  「每个标签自定义颜色」，那就该后端 Tag 实体加 `color` 字段、前端读 `record.color`，
  回到「后端是唯一事实来源」，而不是在前端继续猜。

## 44. ActionForm 加「复制」模式：三分支回填的改法（2026-10-14）

> 由「moneyFlow 账单复制功能」沉淀，第二个用上 useModalForm showCopy 的模块（第一个是 reminder，见 §20）。

- `showCopy(row)` 后 `isCopy=true`、`isEdit=false`、`currentRow=row`，提交走既有 create 分支
  （`isEdit ? update : create`），后端零改动。
- 关键是把「打开回填 effect」从二分改成三分支，漏一个就有明显 bug：
  1. 新增分支：`if (!open || isEdit || isCopy) return;` —— 不排除 `isCopy`，复制数据会被 `resetFields` 清掉；
  2. 编辑/复制分支：`if (!open || (!isEdit && !isCopy) || !currentRow) return;` —— 不把 `isCopy` 纳入，复制打开时根本不回填（表单空白）；
  3. 复制字段值 = 编辑回填基础上改四处：时间→`dayjs()`、备注→`undefined`、`confirm`/`include`→`true`
     （对齐 old 版复制约定：清备注、时间归零、已确认+计入统计），其余（金额/账户/类型/分类/标签/交易对象）与编辑完全相同。
- 复制/编辑态「类型」「账本」都锁定：隐藏类型 Tabs（判据 `!isEdit && !isCopy`）、
  `bookId` 的 Select `disabled={isEdit || isCopy}`（仅纯新增可切类型/账本）。
- 不可复制的行在操作列禁用复制按钮：`disabled={record.type === TYPE_ADJUST}`
  （余额调整 type=4 走账户 adjust 端点，无复制语义）。

## 45. 金额/折算金额 label 标注币种用 code（2026-10-14）

> 由「账单 ActionForm 金额、折算金额输入项写清具体币种」沉淀。

- 跨币种时金额与折算金额是两个不同币种，label 必须写清，否则转账极易填反（转出币种 vs 转入币种）。
- 币种标识用 **code**（USD/CNY）而非 symbol：code 全局唯一；symbol 有撞车（¥=CNY/JPY、$=USD/CAD/AUD…）。对齐统计条 `(USD)` 的既有写法。
- 币种 code 来源走 `currencyApi.options()` 返回的 `CurrencyOption`——它有 `value(=币种id)/label/code/symbol/decimalPlaces`，
  按 id 匹配取 `.code`。**账户列表项 `AccountListItem` 只有 `currencyName/currencySymbol`、没有 `currencyCode`**，
  所以别指望账户数据直接带 code，统一走 currencyOptions 匹配：
  - 金额币种 id = 选了账户→账户币种、未选→账本币种；折算金额币种 id = 转账→转入账户币种、收/支→账本币种（即 §36 的 `amountCurrencyId`/`targetCurrencyId`）。
  - 在这个 id 上 `currencyOptions.find(o => o.value === id)?.code` 现取 code 即可，无需后端加字段。
- 标签用带占位符词条 `金额({code})` / `折算金额({code})`（en `Amount ({code})` / `Converted ({code})`），
  code 缺失时回退原词条（loading 期账本币种未就绪兜底）。
