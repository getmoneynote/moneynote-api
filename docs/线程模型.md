# 线程模型

> 整理日期：2026-11-03。结论：项目是 **Spring MVC（Servlet 线程池模型），不是 WebFlux**。
> 聊天流里的 `Flux` 返回值容易让人误判，本文说明真实线程行为。

## 总览：两个 HTTP 层

应用的线程模型要分两层看，"是否 WebFlux" 只回答第一层的问题：

```
浏览器 ──请求──▶ 【入口层】Tomcat + Spring MVC（Servlet 线程）
                        │
                        │ controller 返回 Flux
                        │ MVC 把 Flux 适配成 Servlet 3.0 异步 + SSE 写出
                        ▼
                【出站层】Spring AI 的 WebClient
                        │
                        └──▶ Reactor Netty event loop ──▶ 大模型 API（DashScope）
```

- **入口层是 Servlet**：所有浏览器请求由 Tomcat 线程池处理，没有 Netty 服务器。
- **出站层是响应式客户端**：Spring AI streaming 内部用 WebClient（默认传输层 Reactor Netty）
  连接大模型 API。Netty 在这里是 **HTTP 客户端**身份，不是服务器。它在 JVM 内维护一组
  `reactor-http-nio-N` event loop 线程（数量 = CPU 核数），负责接收大模型推回的流式 chunk。
- 两层独立共存。"不是 WebFlux" 与 "存在 Netty event loop 线程" 不矛盾。

## 普通请求

- 一个请求占一个 Tomcat 工作线程（`server.tomcat.threads.max` 默认 200）。
- JPA / JDBC 全程阻塞，请求从头到尾绑在同一根线程上。
- 依赖请求 ThreadLocal 的设施（如 `CurrentUserHolder`）在这条路径上可用。

## 聊天流请求（SSE）

入口：`MessageController.send()` 返回 `Flux<ServerSentEvent<ChatEvent>>`，
`produces = TEXT_EVENT_STREAM_VALUE`。Spring MVC 支持返回响应式类型：检测到 Flux 后由
ReactiveTypeHandler 适配成 **Servlet 3.0 异步请求 + SSE 写出**（效果等价 `SseEmitter`）。

按时间顺序的线程轨迹：

1. **Tomcat 请求线程**：进入 controller → `MessageService.send()` 同步执行
   `llmClientFactory.currentConfig()` 与 `chatTransactionService.initialize()`
   （阶段一 DB 写入），组装好 Flux 后返回。**Tomcat 线程随即释放**，不占 200 的额度。
2. **Netty event loop 线程**：`modelEvents` 来自 WebClient，大模型的每个 chunk 的
   `onNext`/`onComplete` 信号都在 event loop 上发出。链上算子跑在哪根线程，
   取决于上游信号从哪来。
3. **MVC async 线程**（默认 SimpleAsyncTaskExecutor，每条流一根）：MVC 侧把 Flux 的
   事件缓冲后排到 async 线程，阻塞式写响应输出流。**每条进行中的聊天流占一根线程**，
   park 等待每个 chunk。
4. **流尾落库**：`concatWith` 在上游 `onComplete` 的线程（即 Netty event loop）上
   同步订阅尾部 `defer`，`persistTerminal` 的阻塞 JDBC 实际跑在 event loop 上
   ——见下文「已知问题」。

### 异步边界的约束

- **流回调线程没有请求 ThreadLocal**：终态落库（complete/fail/stop）不能查
  `CurrentUserHolder`，所需数据必须在阶段一 initialize 时取出并随上下文传递。
  （`MessageService` 内有对应注释。）

## 已知问题：persistTerminal 阻塞 Netty event loop（已修复 2026-11-03）

### 问题

`MessageService.send()` 流尾的三处 `persistTerminal`（complete / error / cancel）
是同步阻塞 JDBC（短事务写库）：

- `concatWith(Flux.defer(...))`：concat 在上游 `onComplete` 的线程上同步订阅 defer
  → 跑在 **Netty event loop**。
- `onErrorResume(...)`：同理，跑在发出 error 信号的线程（通常也是 event loop）。
- `doOnCancel(...)`：跑在**触发取消的线程**上（cancel 不是向下游传播的信号，
  `publishOn` 管不到它）。

阻塞 event loop 会卡住共享该 loop 的其他 LLM 流。event loop 只服务于 LLM streaming
连接（WebClient 只用于调大模型），本应用并发聊天流极少、落库是毫秒级短事务，
实际影响很小；但属于架构隐患，已按下文方案修复。

### 无效修法（避坑）

- 在链尾加 `subscribeOn(Schedulers.boundedElastic())`：**无效**。`subscribeOn` 只改变
  「谁调用 subscribe」，WebClient 是热数据源，信号仍在 Netty event loop 投递。
- 指望 `publishOn` 统一解决：管不到 `doOnCancel`。
- 把 `initialize()` 也包成 `Mono.fromCallable().subscribeOn(boundedElastic())`：
  **不需要**。`initialize()` 在返回 Flux 之前同步执行，跑在 Tomcat 请求线程上，
  阻塞 JDBC 在 MVC 模型里是正常模式；只有迁 WebFlux（入口换 Netty）后才需要这么包，
  且那样会让 `CurrentUserHolder` 的 ThreadLocal 取数时机变复杂。

### 修复方案（已落地，见 `MessageService.send()`）

把每个阻塞调用单独搬到 boundedElastic（保持事件顺序不变）：

```java
// finish 路径：落库完成后再发 finish；事件经 defer 延迟构造，
// 保证 seq.incrementAndGet() 仍在落库后递增（直接 Flux.just 会在装配期提前消费 seq）
.concatWith(Mono.fromRunnable(() -> persistTerminal(..., STATUS_COMPLETED, ...))
        .subscribeOn(Schedulers.boundedElastic())
        .thenMany(Flux.defer(() -> Flux.just(finishEvent))))

// error 路径同理
.onErrorResume(e -> Mono.fromRunnable(() -> persistTerminal(..., STATUS_ERROR, ...))
        .subscribeOn(Schedulers.boundedElastic())
        .then(Mono.fromSupplier(() -> errorEvent)))

// cancel 路径：回调同步执行，用 schedule 挪走（fire-and-forget）
.doOnCancel(() -> Schedulers.boundedElastic()
        .schedule(() -> persistTerminal(..., STATUS_STOPPED, ...)))
```

## 结论与选型建议

- **不迁 WebFlux**：数据访问层是阻塞式 JPA/JDBC，迁了也要 `boundedElastic` 包装，
  收益有限、风险大。
- 如需支撑大量并发聊天流，Java 21 的正解是 `spring.threads.virtual.enabled=true`
  （Tomcat 与 MVC async 都换虚拟线程，阻塞代码不用改），而不是换技术栈。当前未开启。

## 关键代码位置

- `MessageController.java` —— SSE 入口，返回 `Flux<ServerSentEvent<ChatEvent>>`；帧构建委托 `chat.event.SseTransport`
- `MessageService.java` —— `send()` 入口装配（校验 / 配置解析 / initialize / 上下文），不含 Reactor 链
- `chat/stream/GenerationPipeline.java` —— 流式生命周期编排（start → 事件流 → 终态 → finish / error / cancel）
- `chat/stream/TerminalFinalizer.java` —— 唯一终态 CAS + 三处 `subscribeOn(boundedElastic)` 落库
- `ChatTransactionService.java` —— 阶段一 initialize / 阶段三 complete·fail·stop 短事务
- `backend/pom.xml` —— 只有 `spring-boot-starter-web`（无 webflux）
