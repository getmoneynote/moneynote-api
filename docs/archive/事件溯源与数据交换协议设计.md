## 1. 背景与动机

MoneyNote 是开源、自托管的个人 / 小企业记账应用，单体架构：

- Java 21、Spring Boot 4.1、Spring Data JPA / Hibernate
- React + Umi + Ant Design Pro
- 数据库类型不固定（MySQL / PostgreSQL / H2，未来可能更多），JPA 自动建表，业务层不能依赖特定方言
- 实体主键目前统一为 `Long + IDENTITY`

传统备份是数据库状态的直接导出，Backup Format 与当前 Schema、JPA Entity 强耦合。一旦数据模型演化（例如 `MoneyFlow` 将来拆为 `Transaction + Entry`），旧备份的长期兼容会很困难。

本文提出以 **Event Sourcing（事件溯源）** 作为长期数据架构：业务事件是事实记录，数据库表是事件流投影出的当前状态。备份、恢复、审计、增量同步都建立在同一套 Event Protocol 之上。

## 2. 核心概念

```text
                         User
                          │
                       Command
                          ↓
                     Domain Logic
                          ↓
                    Domain Event
                          ↓
                    ┌───────────┐
                    │Event Store│  ← Source of Truth
                    └─────┬─────┘
                          ↓
                     Event Stream
                          │
           ┌──────────────┼──────────────┐
           ↓              ↓              ↓
      Projection       Backup          Audit
           ↓              ↓
      Read Model     Event File
           ↓
   MySQL / PostgreSQL / H2
```

三条核心原则：

1. **Event 是已经发生、不可逆的业务事实**（如 `AccountCreated`），不是 UI 动作（不是 `ButtonClicked`）。
2. **Event Store 是 Source of Truth**。
3. **数据库业务表是 Event Stream 的 Projection / Read Model**。

---

## 3. Identity 设计：Database ID 与 Resource ID 分离

当前 `Long + IDENTITY` 只应作为 Database ID，不能作为跨实例的业务身份。

```text
Database ID   Long       数据库内部使用，随实例不同而不同
Resource ID   UUID / ULID 业务对象的长期稳定身份，全局唯一
```

事件和备份只引用 Resource ID：

```json
{ "accountId": "01K8ACCOUNT" }
```

而非：

```json
{ "accountId": 123 }
```

同一张卡从旧实例恢复到新实例后，databaseId 可能从 123 变为 987，但 resourceId 不变，仍表示同一对象。这一设计可独立于完整 ES 先行落地，并直接消除快照备份中的主键重映射问题。

## 4. Event 协议规范

### 4.1 Event 结构

```text
Event
├── eventId        事件自身唯一身份（UUID / ULID）
├── sequence       事件流中的严格逻辑顺序
├── occurredAt     事件发生时间（UTC，ISO-8601）
├── eventType      事件类型（如 AccountCreated）
├── eventVersion   该事件自身的 Schema 版本
├── aggregateType  聚合类型（Account / Category / ...）
├── aggregateId    聚合的 Resource ID
└── payload        事件业务数据
```

示例：

```json
{
  "eventId": "01K8XXXXXX",
  "sequence": 123,
  "occurredAt": "2026-10-01T10:00:00Z",
  "eventType": "AccountCreated",
  "eventVersion": 1,
  "aggregateType": "Account",
  "aggregateId": "01K8ACCOUNT",
  "payload": {
    "accountId": "01K8ACCOUNT",
    "name": "招商银行",
    "currencyId": "01K8CURRENCY"
  }
}
```

### 4.2 字段约定

- **eventId**：UUID 或 ULID，全局唯一，创建后永不改变。
- **sequence**：Replay 的唯一排序依据。不能用 `occurredAt` 排序——时间戳可能相同、系统时钟可能回拨、时间不保证严格顺序。`occurredAt` 是业务时间，`sequence` 是逻辑顺序。
- **occurredAt**：UTC ISO-8601（如 `2026-10-01T10:00:00Z`）。
- **aggregateType / aggregateId**：事件所属聚合的类型与稳定身份。
- **eventVersion**：见 §5。

### 4.3 Event Catalog（第一阶段：粗粒度）

第一阶段只按聚合建 Created / Updated / Deleted，不拆逐字段事件（避免 `AccountNameChanged`、`AccountCurrencyChanged` 式的碎片化）：

| Aggregate | Events |
|---|---|
| Currency | Created / Updated / Deleted |
| Book | Created / Updated / Deleted |
| Account | Created / Updated / Deleted |
| Category | Created / Updated / **Moved** / Deleted |
| Tag | Created / Updated / Deleted |
| Payee | Created / Updated / Deleted |
| Transaction | Created / Updated / Deleted |
| TagRelation | Created / Deleted |
| Reminder | Created / Updated / Deleted |
| Preferences | PreferencesUpdated（最终模型确定后再决定是否拆分） |

### 4.4 Event 不描述数据库操作

禁止把事件设计成数据库变更日志：

```json
{ "type": "INSERT", "table": "t_account", "data": {} }
```

这种写法仍与具体数据库和表结构强耦合。正确事件只描述业务语义（`AccountCreated` + payload），与 MySQL / PostgreSQL / H2 / JPA / Hibernate 均无关。

## 5. Event Schema 演进

- 事件一经发布**不可修改**。Schema 变更通过新版本承载：`TransactionCreated v1` → `v2`。
- 旧事件通过 **Upcaster** 升级为当前模型后再投影：

```text
Old Event v1 → Upcaster → Current Event v2 → Projector
```

- **Event Version ≠ Backup Format Version**，二者独立演进：
  - Format Version：整个备份文件格式（`moneynote-event-backup v1`）。
  - Event Version：某一种事件的结构。
- Event Protocol 是长期 API：即使 `AccountCreated v1` 十年后不再产生，旧备份仍可能依赖它，不能删除。这是 ES 最大的长期维护成本。

## 6. Event Store

### 6.1 第一阶段实现：单表

第一阶段不需要独立的 Event Store 中间件，直接用一张数据库表（对应 `com.moneynote.event.Event`）：

```text
t_event
├── id              数据库主键（Long IDENTITY）
├── user_id         归属用户（存储层归属列，不进入跨实例引用；导出按此过滤，restore 时重新归属）
├── sequence        当前用户事件流中的严格顺序（每用户独立，从 1 开始）
├── occurred_at     事件发生时间（毫秒 Long；协议层序列化为 UTC ISO-8601）
├── event_type      事件名称（如 AccountCreated / AccountUpdated / AccountDeleted）
├── aggregate_id    聚合 Resource ID（UUID/ULID），事件间引用与 replay 定位的稳定身份
└── payload         JSON 文本（LONGVARCHAR，不依赖各库 JSON 类型）
```

> 存储层是 §4 协议层的简化实现：`event_id` / `event_version` / `aggregate_type`
> 尚未独立成列（`event_type` 的名称本身已蕴含聚合类型）。这三个字段待需要
> （去重 / Upcaster 演进）时再补，届时给存量事件补默认值即可。

`payload` 用普通文本存储 JSON，以保证多数据库兼容（不依赖各库 JSON 类型）。

`aggregate_id` 上建有 `(user_id, aggregate_id)` 的普通索引，支撑按聚合重放全部事件这一核心查询路径。

### 6.2 Append Only

- 正常情况下只允许 `INSERT`，禁止 `UPDATE` / `DELETE`。
- 聚合被删除后，其 Created 事件仍保留。最终状态由完整事件流计算。

### 6.3 删除模型：Tombstone Event

```text
AccountCreated → AccountDeleted
```

Projection 结果为「账户不存在」，但 Event Store 中两个事件都保留。删除事件即 Tombstone（墓碑）事件。

> 注：物理投影为 DELETE 与现有外键约束存在冲突，见 §14 待决问题。

## 7. Projection 与写入流程

### 7.1 正常写入

```text
User Action → Command → Validation → Domain Logic
   → Append Event → Project Event → 更新业务表
```

事件追加与投影更新必须在**同一个数据库事务**中：

```sql
BEGIN
  INSERT INTO t_event ...
  UPDATE / INSERT projection ...
COMMIT
```

任一步失败整体回滚，保证事件与当前状态不出现不一致。第一阶段不做异步投影（不需要最终一致性与投影恢复机制）。

### 7.2 投影示例

```text
AccountCreated → Account 表 INSERT
AccountUpdated → Account 表 UPDATE
AccountDeleted → Account 表 DELETE（待决，见 §14）
```

### 7.3 分层约定

Event 不依赖任何 JPA 注解（`@Entity` / `@ManyToOne` 等），推荐分层：

```text
Domain         Command / Event / Aggregate / Business Rule
Application    Command Handler / Event Handler / Projection
Infrastructure JPA / Hibernate / MySQL / PostgreSQL / H2
```

## 8. Backup 协议

### 8.1 定义

Backup 不是「导出所有数据库实体」，而是**导出某个时间点之前的完整 Event Stream**：

```text
Event Store → Export → MoneyNote Event Backup
```

### 8.2 文件组织

```text
backup/
├── manifest.json
└── events.jsonl
```

`events.jsonl` 每行一个事件（JSONL，便于流式追加与按行校验）。

Manifest 示例：

```json
{
  "format": "moneynote-event-backup",
  "formatVersion": 1,
  "backupId": "01K8BACKUP",
  "createdAt": "2026-10-02T00:00:00Z",
  "eventCount": 123456,
  "lastSequence": 123456
}
```

### 8.3 增量备份

Event 天然只增不改，增量备份即区间导出：

```text
Full Backup        Events 1 ~ N
Incremental Backup Events N+1 ~ M
```

无需重新导出全部数据。

## 9. Restore

### 9.1 流程

```text
选择 Backup → 读取 Manifest → 验证 Format Version
→ 验证 Event Stream → 准备目标实例 → Replay Events
→ 生成 Projection → 验证最终状态 → 完成
```

### 9.2 只需要按 sequence replay

```text
Event 1 → Event 2 → ... → Event N
```

按 `sequence ASC` 顺序 replay 即可，**不需要实体导入顺序**（Currency→Book→Account…），也**不需要 oldId → newId 映射**：事件之间通过稳定的 Resource ID 引用，Database ID 在 replay 中重新生成。

### 9.3 Restore 与 Merge 严格分离

第一阶段只实现 **Restore**——目标是**全新 / 空实例**，精确恢复原状态：不处理同名冲突，不做「招商银行 (1)」式自动重命名。

**Merge**（备份数据并入已有数据的实例）是独立问题，需要 Identity Resolution、重复检测、冲突解决、sequence 对齐与用户选择，留待未来单独设计。

### 9.4 User 的处理

User 本身不作为备份数据恢复。备份属于旧实例的 User A；恢复时所有投影归属于目标实例**当前登录用户**，事件中不依赖原数据库 `user_id`。

User 上的冗余字段 `baseCurrencyId` / `currentBookId` 属于用户状态，需有对应事件（如 `BaseCurrencyChanged` / `CurrentBookChanged`，或统一为 `UserPreferencesUpdated`）。

## 10. 一致性、性能与 Replay 策略

- 个人 / 小企业小规模数据，restore 时单事务 replay 全部事件即可。
- 数据量增大后采用批量投影，避免持久化上下文膨胀：

```text
Replay → Batch → flush → clear
```

- 达到百万级事件以上再考虑 Staging + Batch Projection + Async Restore。
- 第一阶段优先保证：正确性、可恢复性、协议稳定性、多数据库兼容、简单、可测试，不追求极端吞吐。

## 11. 测试策略与核心不变量

### 11.1 测试

- **Replay Test**：给定事件序列（Created / Updated / Deleted 交织），replay 后当前状态必须与预期完全一致。
- **Round Trip Test**（最重要）：

```text
Initial State → Generate Events → Export
→ New Empty Instance → Replay → Final State
```

要求 `Original State == Restored State`。

### 11.2 核心不变量

1. Event ID 全局唯一。
2. Sequence 严格递增。
3. Event 不可修改。
4. 相同 Event Stream 确定性地生成相同状态。
5. 业务对象使用稳定的 Resource ID。
6. Event 不依赖数据库内部 ID。
7. Event 不直接描述数据库操作。
8. Backup 不依赖当前数据库 Schema。

## 12. 实施范围与演进路线

### 第一阶段实现

```text
Event Store / Domain Event / Event Append / Projection /
Event Replay / Full Backup / Full Restore / Event Version / Resource ID
```

暂不实现：Event Bus、Kafka、分布式 CQRS、多实例实时同步、Event Store 集群、Saga、分布式事务、多用户 Event Federation。

### 建议的落地分步（降低风险）

| 阶段 | 内容 | 触发条件 |
|---|---|---|
| Phase 0 | 快照 JSON 备份/恢复；实体增加 ULID Resource ID | 满足当前导出/导入需求 |
| Phase 1 | 同事务 append 事件（outbox 模式），暂不声明其为唯一事实源 | 需要审计能力 |
| Phase 2 | 升级为完整 ES：存量迁移、软删投影、Upcaster、投影版本化 | 跨设备同步 / 时间旅行成为真实需求 |

### 未来可自然长出的能力

数据审计、历史版本、Undo / Redo、时间旅行、增量备份、跨设备同步、跨实例迁移、通用数据导入导出、AI 数据操作、第三方数据交换——全部建立在 MoneyNote Event Protocol 之上。

## 13. 设计原则汇总

```text
1. Event 是事实
2. Event Store 是 Source of Truth
3. Database 是 Projection
4. Database ID 不是业务 Identity，Resource ID 才是
5. Event 永不修改，按 Sequence Replay
6. Backup = Event Stream Export；Restore = Event Replay
7. Incremental Backup = 增量 Event Export
8. Event Protocol 与 Database Schema / JPA 解耦
9. Restore 与 Merge 分离
10. Event Version 与 Backup Format Version 分离
11. 相同 Event Stream 必须能确定性恢复相同状态
```

## 14. 待决问题（Draft 阶段必须回答）

> 以下问题在当前版本中没有结论，是方案落地前必须补齐的设计点，评审时请重点关注。

1. **存量数据迁移**：现有数据库已有业务数据、没有任何事件。上线 ES 需要为存量行补 Resource ID 并合成 Created 事件（只是"穿事件外衣的快照"，无真实历史），或事件只对新数据生效（系统存在时间点分叉）。需要明确迁移策略与工程量。
2. **目标实例并非空实例**：注册时 `UserService.initData()` 已自动创建 USD / CNY / "生活账本"。在刚注册的实例 replay 备份会产生重复。需三选一：注册不发初始化事件、restore 前清空、或 restore 接入注册前安装向导。
3. **墓碑事件 vs 物理外键**：`MoneyFlow.account_id` / `category_id` / `payee_id` 等为 nullable=false 的物理外键，被引用的聚合无法物理删除（现在靠 FK 约束返回 409 保护）。投影需改为**软删**（保留行 + deleted 标记），§7.2 的物理 DELETE 投影不成立。
4. **投影确定性的跨版本问题**：汇率换算、BigDecimal 舍入逻辑升级后，用新代码 replay 旧事件流可能得到不同状态。不变量 4 需要投影版本化或 replay 后与快照核对才能跨版本成立。
5. **Sequence 生成机制**：作用域已定为每用户独立、从 1 开始；但 append 时如何分配（max+1 的并发风险 / 独立序列表 / 其他）尚未决定。回滚留空洞是否接受也需明确。
6. **Event Version 的永久维护成本**：所有发布过的 event 版本与 Upcaster 链永远不能删除，需评估这是否与"小团队维护的开源项目"匹配。
