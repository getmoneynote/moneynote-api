最终职责划分

| 层                        | 职责                            |
| ------------------------ | ----------------------------- |
| `api/*.js`          | 业务 API 请求函数和类型定义，例如 `currencyApi`    |
| `request.js / config.js` | HTTP 请求、认证、错误处理、拦截器           |
| `errorThrower`           | 把后端业务失败转换成异常                  |
| `errorHandler`           | 全局统一展示/处理错误                   |
| 页面/Hook                  | 特殊 API 自己捕获并处理错误              |

## 返回值约定：统一解包

所有请求（无论 `useRequest` 还是直接 `await`）拿到的都是**后端响应体的 `data` 字段**，即业务数据本身：

```js
// 直接 await
const accounts = await accountApi.list();   // 就是数组，不是 { success, data }

// useRequest
const { data } = useRequest(accountApi.list); // data 也是同一个数组
```

实现机制（两处配合，缺一不可）：

1. `src/api/request.js`：`umiRequest(...).then(body => body?.data)`，在统一出口解包；
2. `config/config.js` 的 `request.dataField: ''`：让 Umi 生成的 `useRequest` 的
   `formatResult` 变成恒等函数（默认是 `result => result?.data`，会二次解包）。
   这是构建期配置，改动后需重启 dev server 重新生成 `.umi` 临时文件。

外层的 `success` / `message` 不暴露给业务代码：

- `success === false` 由响应拦截器里的 `errorThrower` 转成 `BizError` 抛出；
- HTTP 非 2xx / 超时 / 断网 / 401 由 `errorHandler` 统一弹消息；
- 业务代码只需处理 resolve 出来的 data，或在 `skipErrorHandler: true` 时自己 catch。

## 分页约定：转换只在 BaseProTable 边界

- **请求参数**：API 层（`src/api/`）直接透传后端契约 `page`（0 起）/ `size`，
  不做任何转换；antd ProTable 的 `current`（1 起）/ `pageSize` 只在
  `BaseProTable` 的 request 包装里转成 `page` / `size`。
- **响应结构**：后端分页接口的 data 是 `{ content, current, pageSize, total }`
  （见 `docs/api-response-convention.md`），`BaseProTable` 映射成 ProTable 需要的
  `{ data, total, success }`。
- **效果**：自定义分页接口（不走 `createCrudApi` 的）不需要任何额外处理，
  直接 `request(url, { params: { page, size, ... } })` 即可，消灭了
  「转换只覆盖标准 list、自定义接口容易漏」的坑。
- 页面的 request 函数如果返回 ProTable 结构（非分页列表、空态短路），
  `BaseProTable` 原样透传，两种返回结构都支持。

## `createCrudApi` / `pickCrudApi` 的边界

`crud.js` 只提供标准 CRUD 动词（create / list / update / delete）。
模块特有的接口（如 `options`、`tree`、`move`、`setDefault`）各自定义在
`api/<feature>.js` 里，不要塞进 `crud.js`——不是每个资源都有这些接口。
